## P1 · Decoding speed

2. **Streaming decode core — read-chain and uop attrition.** json x1.24-1.36, skewed x1.10-1.32, text x1.04-1.21, dll x1.34-1.37 (narrowed 2026-09-19 by the fused bit-read; the streaming column is the honest core comparison — own stream-vs-bulk overhead ≤2%). The fused sequence loop is throughput-bound (IPC 3.46-3.57, flat cycle profile), so uop cuts convert ~1:1 into wall — but the loop is one register-allocation domain and every source change re-rolls it (±600-800K Ir on json), each cut a lottery against a ~10 Ir/seq spill set (entry unpacking 6+ uops/sequence, shlx/shrx chains). The fused bit-read proved the one lever that beats the lottery: cutting segments of the *serial* spill chain (the win store-forwarding round trip) converts to IPC even at +Ir. Remaining read-side levers in that family, each its own re-roll: fold the reload's window rebuild into the next read (needs the next entries loaded before the reload), fold `consumed` into `ip`. Every structural lever beyond that is falsified ([negative](negative/decoding.md)); attribution in [decoding](perf/decoding.md).

## P1 · Encoding speed

3. **Fastest — json x1.43; realistic ceiling ~x1.3-1.4.** The steady scan loop is branch/latency-bound (IPC ≈ 3, ~4 cyc/iter of mispredict cost); the remaining mispredict budget is spread across inherent branches (extend_match exits, hash-match compares — libzstd pays the same class). New levers must ship as dense-mode instantiations that keep the plain body byte-for-byte — the hosting class that works (miss-run stepping and batched probing are falsified as unconditional levers; the price bar cannot live in the plain loop body). The dense band gates from 256 KiB up; single-block payloads stay plain. json.fastest.mt8's gap is this per-core deficit scaled through workers. [matchers](perf/matchers.md), [negative](negative/matchers.md).
4. **Small/mid payloads (4K-1M)**: the open speed item is the fastest tier's 64K-1M cells (x~1.36-1.48 json/text) — the same steady-scan deficit and ceiling as item 3, plus the emit-side instruction-volume floor (register-budget-bound; C-parity restructures falsified). Below 64K the fixed-cost side is closed: the per-block Huffman build, FSE CTable build, weight materialization, table serialization and the pooled-table struct moves are all at/below C parity ([encoding](perf/encoding.md)); what is left on a json-4K call is the plain-body scan of item 3 and that emit floor.
