## P1 · Decoding speed

3. **Streaming decode core residue — x1.27-1.35 json, x1.10-1.32 skewed, x1.04-1.21 text** (2026-09-14 pass). The streaming column is the honest core comparison (zstd's bulk API is a slow wrapper; our own stream-vs-bulk overhead is ≤2%), so this is the fused sequence loop vs libzstd's pipeline, not a wrapper cost. The loop is at its serial-chain limit — IPC ~3.7, register wall, and every in-loop structural rework is falsified ([negative.md](negative.md)). The one structural lever left untried: a **libzstd-style 8-deep sequence ring-buffer pipeline** (decode a batch of sequences into a ring while earlier ones still execute, overlapping FSE-state-chain latency with match copies). negative.md's decode rows only gate this on a benefit/risk assessment — do that first: (a) perf-attribute the loop per shape to confirm the FSE chain (not the copies) is the critical path where we lose (json yes; text is copy-dominated and already near-parity); (b) budget the ring's live values — the ring must live in memory (like libzstd's `seqState`/`DSeq` split), never as new registers (the repcode-registerization falsification is the precedent); (c) it only pays where the gap is ≥1.2×, i.e. json/skewed.

## P1 · Encoding speed

4. **Fastest — json x1.57 vs libzstd-1** (2026-09-14; was 1.67 — the emit-inline/hash-mask/pack_seq lands moved it; largest single low-tier speed gap). The steady scan loop is branch/latency-bound, not instruction-bound: IPC ≈ 3, ~14 cyc/iter vs a ~4-5 cyc port floor, ~4.6 cyc/iter of it branch-mispredict cost (~9 branches/pair vs libzstd's ~5). Levers left: deeper hash pipelining for miss runs (blocked on register headroom, no identified source); otherwise profile first to localize. Emit-state residency, rep-probe policy halving and insert_covered AVX-512 batching are all falsified ([negative.md](negative.md)).
5. **Fast — json x1.11** (was 1.13). The per-sequence encode path is near-tight. Remaining: the concat's variable shifts + the writer's shift/OR/flush (~10.7% of json.fast cycles), the three-channel SIMD histogram in choose_tables_fast (2.2% of cycles — caps the win low), and the dfast matcher itself (still the dominant share of json.fast cycles). Position-u64 carry and seqStore-cursor emit are falsified ([negative.md](negative.md)).
6. **Balanced — json x1.34 vs zstd-9** (2026-09-14; was 1.40 after the pipelined head reads; interleaved) while carrying +19.5% density (7.11 vs 5.95), so the fair comparison is zstd-8/9 territory. Closed model: the two steady chain-walk copies are a latency-bound chain-link chase (82% of cycles, 93% of L1 misses, ~66 cyc/step ≈ one serialized L3-class load) — Ir/register work no longer converts to wall ([negative.md](negative.md)). What remains latency-side is only the chain-link chase itself (irreducible: each link's address depends on the previous link's value, software prefetch cannot chase pointer chains) and the scan walk's own exposed head read (no +1 carry exists — the miss path and emits move pos unpredictably). Table sizing is ratio-locked (C20 minimal-exact for W21), the second-chance search is ratio-load-bearing.
7. **Best/Opt/Ultra speed** (ratio already ahead/level): **Best is the largest wall gap in the codec — json x4.22 / skewed x6.22 / text x1.77 (2026-09-14), and it caps every streaming column** (json.best stream x4.05 ST / x3.31 mt8). Also: text Opt 313 vs libzstd ~440 MiB/s, Best's per-block DP cost behind 12-19 MiB/s, streaming MT per-job fixed cost (text.best streaming 0.8× its own ST), and W22/W23's json-specific cost (solo Opt 6.05s, footprint 96MiB after the C22 relief — the reach pays only on dll-class data); all of it is walk/DP cost over the wider candidate space (profile with enc_prof + perf). Ultra dll residue: 7.7% sparser than zstd-19 at same knobs (suspects: search/pricing subtleties, per-block DP cost).
