## P1 · Encoding speed

3. **Fastest — json ~1.57× vs libzstd-1** (largest single speed gap). The steady scan loop is branch/latency-bound, not instruction-bound: IPC ≈ 3, ~14 cyc/iter vs a ~4-5 cyc port floor, ~4.6 cyc/iter of it branch-mispredict cost (~9 branches/pair vs libzstd's ~5). Levers left: deeper hash pipelining for miss runs (blocked on register headroom, no identified source); otherwise profile first to localize. Emit-state residency, rep-probe policy halving and insert_covered AVX-512 batching are all falsified ([negative.md](negative.md)).
4. **Fast — json x1.13**. The per-sequence encode path is near-tight. Remaining: the concat's variable shifts + the writer's shift/OR/flush (~10.7% of json.fast cycles), the three-channel SIMD histogram in choose_tables_fast (2.2% of cycles — caps the win low), and the dfast matcher itself (still the dominant share of json.fast cycles). Position-u64 carry and seqStore-cursor emit are falsified ([negative.md](negative.md)).
5. **Balanced — json x1.40 vs zstd-9** (interleaved) while carrying +23.7% density (7.12 vs 5.76), so the fair comparison is zstd-8/9 territory. Closed model: the two steady chain-walk copies are a latency-bound chain-link chase (82% of cycles, 93% of L1 misses, ~66 cyc/step ≈ one serialized L3-class load) — Ir/register work no longer converts to wall ([negative.md](negative.md)). The named latency lever landed 2026-09-14 (pipelined hash+head for the lazy walk's searches: dll +4.5%, json +1.5-2%, text +1.4%, skewed −2% — see [matchers](perf/matchers.md)); what remains latency-side is only the chain-link chase itself (irreducible: each link's address depends on the previous link's value, software prefetch cannot chase pointer chains) and the scan walk's own exposed head read (no +1 carry exists — the miss path and emits move pos unpredictably). Table sizing is ratio-locked (C20 minimal-exact for W21), the second-chance search is ratio-load-bearing.
6. **Best/Opt/Ultra speed** (ratio already ahead/level): text Opt 313 vs libzstd ~440 MiB/s, Best's per-block DP cost behind 12-19 MiB/s, streaming MT per-job fixed cost (text.best streaming 0.8× its own ST), and W22/W23's json-specific cost (solo Opt 6.05s, footprint 96MiB after the C22 relief — the reach pays only on dll-class data); all of it is walk/DP cost over the wider candidate space (profile with enc_prof + perf). Ultra dll residue: 7.7% sparser than zstd-19 at same knobs (suspects: search/pricing subtleties, per-block DP cost).
7. **Small/mid payloads (4K-1M)**: small end closed (json-4KiB ratio ±1-5% since the small-literal huffman fix; the dict residue is item 10). Open: mid-size json/text ~2× speed — per-byte scan+emit cost, not fixed overhead (table build is done).
8. **Large-binary ST encode (100MB-class)**: windows closed; the remaining gap is pure per-byte cost — fast x1.35 (359 vs ~480-560 MB/s), balanced x2.24 (x2.14 after the 2026-09-14 pipelined head reads). dll's 25% literal fraction puts huff0+compress_literals at ~20% of fastest cycles (huff0 stream itself at libzstd parity); scan/emit miss loops are at libzstd parity.
