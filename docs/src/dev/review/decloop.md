# Sequence-loop port review

Scope: commit `c50d6f73`, "dec: port libzstd's sequence loop structure into the flat executor", which rewrote `crates/zstdx/src/decoding/sequence_execution.rs` and `crates/zstdx/src/decoding/sequence_section_decoder.rs`. Reference: `ZSTD_decompressSequences_body`, `ZSTD_decodeSequence`, `ZSTD_execSequence` and `ZSTD_execSequenceEnd` in libzstd 1.5.7 at `/root/programs/fork/zstd/lib/decompress/zstd_decompress_block.c`, plus `OF_base`/`OF_bits` in `lib/decompress/zstd_decompress_internal.h`. This was a review-only round: no library code changed, and every actionable finding is a next-round candidate, because concurrent tracks own these files.

## Method

The commit diff and the landed code were read side by side against the C reference. Every memory-safety precondition was then traced to its enforcement site: the HEADROOM chain from `FlatOut::ensure_block_space` through `decompress_block_flat`'s target truncation into the executor's `oend_w`, the literals tail through `zero_wildcopy_tail`, and the repcode writeback through `DecoderScratch::reset` and the frame-decoder error paths. `cargo test -p zstdx` is green on the branch, and `cargo clippy --release -p zstdx` reports four warnings, all pre-existing in `encoding/btlazy.rs`, `encoding/opt.rs` and `stream/encoder_mt.rs`, none in the ported files.

## Safety verdict: sound

The unconditional 16-byte literal copy is bounded on every path that reaches it.

Write side. The hot path admits a sequence only under `o_match_end <= oend_w`. The largest wildcopy overshoot past a sequence end is 15 bytes: `wildcopy16` and the 16-byte chunk loop of `wildcopy_match` write up to 15 past their end cursor, and `overlap_copy8` writes at most 8. Without headroom, `oend_w` sits 16 bytes below the target end, so every store stays inside the caller's slice. With headroom, `decompress_block_flat` truncates the target to `block_limit = written + block_out_max` before the executor sees it (`block_decoder.rs`), and `ensure_block_space` guarantees the backing allocation holds `block_max + WILDCOPY_SLACK` beyond the cursor (`flat_buffer.rs:228`). So the stores land in `out_end + 15` at most, inside the 16-byte slack, for the literal loop, the 16-byte match loop, the 8-byte overlap loop and the wrapped-source wildcopy alike. The `exec_sequence_end` paths never overshoot: they check `o_match_end > out_end` first and copy exact lengths, and their `wild` copies only run under the headroom instantiation after the same end check.

Read side. `zero_wildcopy_tail` runs before every flat execution (`block_decoder.rs:221`) and keeps `[len, len+16)` of the literals buffer allocated and zeroed, which covers the over-read of `copy16` and `wildcopy16` at any literal cursor, including an empty literals buffer, where `reserve(16)` gives `as_ptr` a real 16-byte allocation. The hot path checks `i_lit_end > lit_end` before the copy, and the exact path re-checks `*lit + ll > lit_end` before its plain copy.

Wrapped-generation reads. `copy_wrapped_match`'s wild fast path reads up to 15 bytes past `src + ml`. The guard `d >= ml && offset + ml <= seg_a_end` plus the hot-path budget bounds that read end at the previous generation's physical end plus 15, and the last block decoded in that generation had `end + block_max + WILDCOPY_SLACK` of buffer behind it, so the read stays inside the allocation and inside zero-initialized bytes (`buf.resize(target, 0)` growth).

Repcode history. The three locals are written back to `offset_hist` only on loop success; every error return inside the loop discards them, so a mid-block abort leaves the last successful block's history in place. Frame reuse reinitializes it: `DecoderScratch::reset` restores `[1, 4, 8]` (`scratch.rs:45`), and both `FrameDecoderState::new` and `reset` route through it. A poisoned history cannot leak into a pooled decoder's next frame. One ordering divergence exists and is unobservable: libzstd saves the reps after its `BIT_endOfDStream` check, zstdx writes back before `finish`, so a frame that fails the final padding check leaves different rep values behind. Both treat the frame as errored, and the next frame resets the history.

## Parity checks

- Field read order matches `ZSTD_decodeSequence` exactly: offset add-bits inside the offset branch, then match length, then the mid-sequence reload when `ll_bits + ml_bits + of_bits >= 31`, then literal length, then, for every sequence but the last, the three transitions in LL, ML, OF order followed by the end-of-sequence reload. The 31-bit threshold equals libzstd's `STREAM_ACCUMULATOR_MIN_64 - (LLFSELog+MLFSELog+OffFSELog)`, and the last sequence skips transitions and reload exactly as `isLastSeq` does. Initial states read in libzstd's LL, OF, ML order.
- The offset tables agree code by code. `OF_CODES` packs base `1 << code` and the executor subtracts 3 at use; libzstd pre-folds the same subtraction into `OF_base` (`0, 1, 1, 5, 13, 29, ...` with `OF_bits = code`). Codes 2 through 5 were checked value by value; real offsets cover the same ranges on both sides.
- Repcode semantics match. Code 0 resolves `rep[ll0]` with libzstd's history shuffle, and code 1 forms `idx = of_base - 1 + ll0 + bit`, which equals libzstd's wire value 1 to 3, with `idx == 1` selecting rep1, 2 rep2, 3 the `rep0 - 1` pseudo-slot, and `idx != 1` gating the rep2 rotation exactly as libzstd's `offset != 1` does. The zero guard is stricter than libzstd's `temp -= !temp` wrap: a dictionary-seeded zero history saturates and lands on the explicit `ZeroOffset` rejection.
- The combined check `i_lit_end > lit_end || o_match_end > oend_w` covers the same edge cases as libzstd's `iLitEnd > litLimit || oMatchEnd > oend_w`, and `exec_sequence_end` re-checks in libzstd's order: end-versus-target first, then literals, then the offset reach `offset > o_lit_end - virtual_start`.
- The `ofBits > 1` branch keeps libzstd's semantics: codes 2 and up read their add-bits inside the branch, rotate the history with three moves and never touch the zero guard, since `of_base + bits - 3 >= 1`.

## Findings

1. Low, next-round. Stale references to functions the commit deleted. `sequence_execution.rs:779` names `exec_one_flat` in `copy_wrapped_match`'s dispatch comment, `block_decoder.rs:38` and `block_decoder.rs:217` name `wildcopy_literals` in `zero_wildcopy_tail`'s contract, and `docs/src/dev/comparison.md` cited both. The comparison page is fixed in this round; the code comments belong to files under concurrent rewrite and are recorded here for the owning tracks.
2. Low, next-round. The inline repcode rotation in `execute_decoded_flat_inner` and `do_offset_history` implement the same spec table in two shapes, branchy locals and select form. `do_offset_history` carries the reference unit test; the inline form is pinned only end-to-end through the parity and corrupt gates. A regression test that pins the inline shape would need a factored form, and factoring it risks the loop's live set, so the gap is recorded rather than closed.
3. Informational. The hot path computes `op + ll` and `o_lit_end + ml` with non-wrapping adds where libzstd carries an explicit `MEM_32bits()` overflow guard in the combined check. On 32-bit targets the adds cannot wrap in practice, because both lengths stay under 132 KB while user-space allocations sit far below `usize::MAX`, but the reasoning is implicit. A one-line comment at the add sites would pin it.
4. Informational. `exec_sequence_end` takes `HEADROOM` as a runtime `bool` while `NOWRAP` stays a const generic, and its `out_base` parameter is read only under `seq_dump`. Both are deliberate cold-path choices; noting them here so a future reader does not mistake them for port debris.

## Verified clean

- The port left no dead code: `exec_one_flat`, `wildcopy_literals`, `decode_step_wide` and the `FUSED` generic are gone, and `SEQ_TABLE_SLOTS` remains live through `scratch.rs:151`. The staging `decode_step` keeps its batched two-read body and wire offsets, which MT stage A requires, and the divergence from the flat loop's per-field body is documented on both sides.
- The packed entry layout moved to libzstd's `ZSTD_seqSymbol` field order with endian-specific `EntryRef` offsets, and `entry_field_loads_match_shift_extraction` pins the load form against the shift form on both endiannesses.
- Comment placement follows the line-precise rule: every `unsafe` block carries a local SAFETY argument, and the loop's load-bearing choices (the unconditional copy, the reload threshold, the last-sequence skip) are annotated at their sites.

## Round 2: the 2026-11-02/03 decode landings

Scope: `f14cd409` (the staged executor port into MT stage B), `64b84806` (zero-sequence literals blocks decoded straight into the flat target), `9b01a64e` (one-shot block bodies parsed in place off the input slice) and `903cb57d` plus `0d42195d` (the FSE spread slice-width shift and the X1 Huffman rank fill). The stage-A pool landing `f2df78ca` has its own page, [decpool](decpool.md). Round 2 was review-only as well: no library code changed, and `cargo nextest run -p zstdx` is green, 494 passed.

### f14cd409, staged executor: sound

The staged loop copies literals unconditionally in 16-byte chunks, so its reads can pass the block's staged literals by up to 15 bytes. `decode_segment` appends 16 zero bytes after the whole segment's literals (`mt.rs:664`), and the staging pool clears before reuse, so the overread of the segment's last block lands in that tail while an interior block reads the next block's staged literals. A zero-length literal run still copies one 16-byte chunk, because `copy16_chunks` writes its first chunk unconditionally; its read stays under the same tail argument and its write stays in bounds because the combined check forces `o_match_end` at or below `oend_w`, which is the region bound minus 16. The piece executor in `mt_pieces.rs` calls the same `execute_blocks`, so it inherits the tail and the checks; its sentinel history `[u32::MAX; 3]` and `validate_piece`'s `do_offset_history` walk are arithmetic only, and execution re-checks every offset, so a divergence between the two selector shapes could only error a piece, never corrupt it.

The block budget is derived from the same staged data the loop consumes, literals plus a saturating sum of match lengths, so `op + rest` lands at or below `budget_end` structurally and the trailing `TargetTooSmall` check is unreachable belt-and-braces. `oend_w` as the minimum of the write limit and the wild cap minus 16 bounds every wildcopy overshoot: the overlap path writes at most 7 bytes past `o_match_end`, the 16-byte path at most 15. `exec_staged_end` re-checks the budget, the literals and the offset in that order with exact copies, and its reliance on `budget_end` in place of the region bound holds because the piece path cuts `budget_end` at the piece end and the segment path at the placed region.

The repcode history lives in locals for the block run and is written back after the sequence loop, before the unreachable trailing check. Every reachable error path returns before the writeback, and both MT drivers hold the history as a call local (`mt.rs:1206`, `mt_pieces.rs:990`) that every frame start resets, so a pooled decoder cannot inherit a partial history. The inline selector mapping was checked case by case against `do_offset_history`: wire value plus `ll0` forms the slot index, slot 3 is the saturating `rep0 - 1` pseudo slot, and the keep, swap and rotate gating agrees on all six wire-and-`ll0` combinations.

Findings:

1. Low, next-round. The comment at `mt.rs:917` says the staged match length of at least 3 keeps the sub-16-offset path's 8-byte writes inside it. The bound that actually holds those writes is the `oend_w` slack: `overlap_copy8` writes 8 bytes for a 3-byte match and overshoots the match end by up to 5 bytes. The floor of 3 is real, from `ML_CODES`, but the comment names the wrong mechanism and should be reworded.
2. Informational. The hot path computes `op + ll` and `o_lit_end + ml` as plain adds, the same 32-bit overflow class as round 1's item 3. The saturation guards in stage A keep the block budget below the block maximum, so the reasoning holds through the same implicit allocation-limit argument.

### 64b84806, direct zero-sequence literals: sound

The peek is read-only. A first sequence-section byte of zero encodes a zero sequence count unambiguously, the real `SequencesHeader` parse still runs in its original position, and the flat path's rejection of trailing bytes after a zero-count header is unchanged, so a malformed frame meets the same verdicts at the same positions and no bitstream state moves.

The direct fit check at `block_decoder.rs:461` runs against the full target before the `block_limit` truncation. This is safe because `parse_sections_body` rejects a regenerated size above the block maximum first (`block_decoder.rs:414`), so a direct write can never pass `block_limit`, and a target too small declines the direct path so staging reports `TargetTooSmall` where it always did. `decode_literals_direct` runs `prepare_section_table` and `parse_stream_bounds`, the same checks in the same order as the staging path, and its late gate returns `Ok(false)` after which staging re-runs them, so error verdicts keep their type and position. The checksum sees identical bytes, because the direct decode fills exactly the range the staging copy produced.

The interleaved loops bound their writes off `out.len()`, the iteration cap and `finish_streams`' segment ends, so the caller's target sees the same discipline the staging slice did. What the direct path loses is the staging side's debug poison margin around the published region (`literals_section_decoder.rs:224`): a bounds bug in the interleave has no debug instrumentation when a zero-sequence block takes the direct gate. Low, next-round: either accept the hole with this record or add a debug-only shadow check.

### 9b01a64e, in-place block bodies: sound

`decompress_block_flat_slice` splits the body with `source.get(..content_size)` and reports the reader path's `UnexpectedEof` on a short body. The body borrow is immutable, consumed inside the call frame, and `parse_sections_body`'s returned raw slice never escapes `decompress_block_flat_body`. The input is advanced past the block before the decode, which matches the reader path's consumption on error paths. No path writes into or retains the input, and the target cannot alias the input because both are outstanding borrows at the call site, so an in-place decode is rejected by construction rather than by convention. The scratch is destructured field by field so the body borrow coexists with the mutable scratch borrows, and the staging `block_content_buffer` stays untouched on the slice path.

### 903cb57d plus 0d42195d, table-build fills: sound

The slice-width shift rests on `num_state_slices` being a power of two that divides the power-of-two table total, which the round-up construction gives for every probability. The pin test in `fse_decoder.rs` is exhaustive over that domain, every probability from 1 to the total for totals 16 through 512, which covers the reachable table sizes, the single-slice shape at probability 1 and the full-width shape at probability equal to the total.

The rank fill sorts symbols by code length with `u16` cursors, which fit because the symbol count caps at 256, then writes each rank's spans longest-code first under one running cursor. A validated weight set satisfies Kraft equality, so the cursor lands exactly on `decode.len()`, pinned by the debug assertion. Every fill in the new code is a safe `slice::fill` on the `u16` view: exact-length writes, no alignment hazard, and no unsafe stride fill anywhere. The equivalence test pins the single-symbol and flat-table seeds explicitly, its generated sets reach width 11, its rejection rules enforce the tree rule, and both weight-header encodings are exercised, with every sixteenth set forced through the FSE path. The scatter reference stays honest because it runs after `build_decoder` left `rank_indexes` at their initial region starts, which the new fill no longer consumes. An empty weight set is not a fill shape, because `build_decoder` rejects it before the fill runs.

Informational: a weight set that somehow passed validation with an incomplete tree would leave stale slots in the table exactly as the scatter fill did, so the exposure is unchanged rather than new.

## Round 3: the 2026-11-04 in-dst literals staging

Scope: the flat one-shot path's third literals placement, `LiteralsPlacement::InDst` in `block_decoder.rs`, porting libzstd 1.5.7's `ZSTD_in_dst` arrangement from `ZSTD_allocateLiteralsBuffer`. Review-only record of the contract the placement adds; the mechanism's decomposition lives on the [dec-gap](../bench/dec-gap.md) page.

Bounds. The staging region sits at `out[written + block_out_max + 16 .. + 16 + lit]`. The pad's lower edge is one past the executor's maximum store: every wildcopy store stops at `block_limit - 1`, because `oend_w` sits 16 below the target end on the non-HEADROOM instantiation and the wildcopy overshoot is at most 15. The tail keeps 16 readable bytes above the literals end for the executor's over-read of at most 15 bytes; both ride inside the caller's target through the same `checked_add` gate that admits the placement, so no slack beyond the target is ever touched. A zero-length literals run cannot reach the placement: a block with zero sequences takes the direct-at-cursor decode, and a block with sequences carries at least one literal per the section's own accounting.

Fallback. A declined gate, a single-stream Huffman section, a target without room, or any HEADROOM caller keeps the scratch staging path with the 16-byte zeroed tail, and error types and positions stay where the staging path reports them, because the in-dst decode runs the same `decode_literals_direct` body the zero-sequence fast path already runs and its declines return `Ok(false)` before any bytes move.

Streaming refusal. The HEADROOM paths never take the placement: their windowed buffer keeps the previous generation physically above the write cursor, where the staging region would sit, and `copy_wrapped_match` reads that region, so staging bytes could leak into match output. This mirrors libzstd's own `streaming == not_streaming` gate on `ZSTD_allocateLiteralsBuffer`.

Codegen. The in-dst block executes through `decompress_block_flat_indst`, an out-of-line twin: a second literal source inlined at the staged call site re-rolls the fused loop's register allocation, and json-class shapes pay that per sequence. With the twin, instruction counts on json, text and random cells read equal to the base build while the placement declines, and the landed json and text cells measured flat under the locked batch.
