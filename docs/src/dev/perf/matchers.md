# Performance Optimization · Matchers and Compression Levels

## Strategy ladder (current)

| Level | ≈zstd | Strategy | Key parameters |
|---|---|---|---|
| Uncompressed | 0 | raw blocks | — |
| Fastest | 1 | fast: hash5 single-probe table | window 768KiB, table 2^15 u32, ml≥6 threshold, miss step `(miss>>2).min(255)`, rep0 pre-probe + rep1 chain |
| Fast | 3-5 | dfast: hash8 2^17 + hash5 2^16 dual-table single-probe | window 2MiB (W21), 4-anchor backfill after matches, stateless anchor miss step |
| Balanced | 6-9 | hash chain + lazy | W2MiB / H20 / C20 / depth 8 / lazy, u32 tables |
| Best | 13-15 | btlazy2: lazy2 selection over the DUBT tree | W22 / H22-23, S4/5/6 search (C's L13-15 rows), mls 5, literal-aware lazy margins |
| Opt | 16-17 | btopt (full port) | W23 / H22 / C22 (L17 row, ring capped one below libzstd's C23) |
| Ultra | 18-22 | btultra(+2) | W23 / H22 / C23, 2-pass first-block statistics seeding |

## Fastest (fast)

- **zstd-fast style rewrite**: contiguous window + single-probe u64 hash table (originally `epoch<<48|pos` slots, reset only bumped the epoch to skip clearing; later `327bc99` switched to u32 and retired the epoch), hash5 (u32 + the 5th byte), u64-chunk compare forward/backward extension (backward extension goes into pending literals), increasing miss step. Matching ~3×, text ratio leapt 54× (the old matcher was nearly defunct on long-repetition data). `a2cc982`
- **repcode**: the matcher maintains rep[3] (sharing `do_offset_history` semantics with the decoder); ll==0 uses the **pos+1 probe** (the current byte acts as that 1 literal, backward extension guarded by `start > anchor+1`); emits of_value (1=rep0, new offset=offset+3). json rep hit rate 0.07%→7.6%. `1d25a26`
- rep1 immediate chain probing (zstd rep_offset2 loop, ll==0 auto-swaps rep0/rep1): json ratio 4.93→5.23. `49de097`
- **sparse indexing**: ≤16B insert everything, >16B insert only the start+2/end-2 dual anchors (keeps json's long-distance matches better than zstd's pure dual anchors; pure anchors cost json -2.1%/text -6.3% ratio). json +6%. `4e79929`
- table 2^16→**2^15** + strided insertion on the miss path: small table with high contention + newest-wins = strong proximity bias (zstd -1 is 2^14 slots against a 512K window = 32:1 coverage). `21fb329`
- hash path **ml≥6 threshold**: a 5-byte match's sequence cost ≈ the cost of the literals it covers, so rejecting it lets the scan advance toward longer match starts (tried 7/8: json saturated, text collapsed; 6 is the balance point). json 5.44→5.72. `be2bfe9`
- window 448K→**768K**: the text corpus's tile period falls in 512K-768K, unlocking cross-tile matches. text ratio 6.46→239. `7a2a388`
- **select-based probing** (libzstd selectAddr): invalid candidates are selected into the scan position itself; byte compare + single-branch rejection via `cand != ip` replaces the epoch/win_base/distance triple compare; the rep0 pre-probe folds into the single comparison `probe >= win_base + rep[0]`. json 455→466 MiB/s. `29bcb02`
- `TableEmit` context struct replaces the 12-14-parameter free function (guards against parameter stack spilling); scan-side table access via raw pointers. `c528c57`
- **emit split**: the coverage-indexing loop moved out of `TableEmit::emit` into an `#[inline(never)] insert_covered` — with it inline, emit exceeded the inliner budget and each of the scan loop's five call sites paid a full spill/reload of the emit context (literals/seqs/rep) plus a hash-constant rematerialization around the call (the call prologue/epilogue alone sampled ~9% on json.fastest). Splitting leaves emit small enough to inline at every site. Byte-identical output; gungraun json.fastest -2.7%, text.fastest -1.1% instructions.
- **two-phase scan loop**: the job-start seed/gate state (`seed_offset`/`seed_hits`/`seed_budget`, `rep_pending`) only ever winds down, so the body is a macro instantiated twice — a seeded phase until convergence, then a steady phase with all four values constant-folded out. One loop kept them live across every iteration (pure dead weight in bulk-ST and post-convergence MT jobs), and ~24% of the scan's cycles sat on stack spill/reload traffic. Byte-identical; gungraun fastest json/text −10.1%/−10.0% Ir, random −2.0%; wall json.fastest 477→532 MiB/s (x1.78→1.60 vs zstd-1), text.fastest 11279→12855. Companion: `rep1_chain` moved to `inline(always)` — duplicating the body halves the inliner's budget per copy, and left to its own judgment the helper flips to an outlined call whose argument setup dominates dense-match emits (json was at −3.1% Ir before that fix, the emit-split lesson running in reverse); forcing it doubled the win.
- **steady-body slimming (2026-09-11)**: three pure overhead cuts, byte-identical, wall-neutral on json (the loop is branch/latency-bound, IPC ≈ 3): the pair-prep u64 feeds hash5, the 4-byte prefilter (its low half) and the rep compares (two loads per pair gone); the rep probes compare in window-index space (`pidx >= rep[0]`), deleting the per-position `rep0_lim = win_base + rep[0]` u64 chain and its spill; and the fast/dfast `resolve` rebuilds the candidate as a *distance* — `dist = pos − entry + 1` (double-wrapping, no `entry−1` underflow) wraps huge for the empty sentinel (dist = pos+1) and previous-4-GiB-cycle entries, so the single compare `dist <= reach` (reach = min(pos−win_base, max_window)) replaces the entry==0 / wrap / window triple check and returns `idx − dist` directly. gungraun fastest json/text −5.9%/−5.7% Ir; random +1.35% (miss path pays two extra ALU per empty probe, wall unmoved at 2.3 GiB/s). The `pos1 == anchor` select in the second probe is provably dead (anchor ≤ pos < pos+1) and folded out. A steady/tail loop split folding `pair_len` to a constant 2 was dropped: −3.3% Ir but text.fastest wall −7% — the third macro instantiation displaces the hot blocks (see negative.md).
- **OR-folded pair rep prefilter (2026-09-11)**: the pair's two repcode compares (one per position) collapse into one unpredictable branch — XOR prefilters `a`/`b` over the same loads, taken when either is zero (adjacent-position rep hits are correlated, so the fold predicts no worse than either compare alone); a taken fold whose first position misses arms the second position's compare-free full probe, and probe/emission order is untouched → byte-identical output (dump-gated). The branch-bound regime's expected trade: gungraun fastest json/text +1.5%/+1.4% Ir for wall json.fastest 530→545 MiB/s (x1.62→1.57 vs zstd-1); text.fastest −1.4% sits inside that cell's layout-noise band (untouched fast cells moved ±3-8% in the same binary), skewed/random flat. The probe-*count* cannot drop instead: halving it (libzstd's ip2 one-compare-per-pair policy) costs json.fastest +4.75% size — see negative.md.
- **dead-mask drop in the hash helpers (2026-09-13)**: `>> (64 - log)` already leaves exactly `log` bits, so the `& ((1 << log) - 1)` in `hash5_log`/`hash_at_log`/`hash8_at_log` was provably dead — but with a runtime `log` LLVM cannot prove that and rebuilds the mask (`mov -1; shl cl; not; and`) per hash: hoisted out of the steady scan loops, but per-call inside any outlined body (the chain walk rebuilt it every search). Dropping the AND is byte-identical by construction (full-ladder dump gate); gungraun fastest json/text −5.2%/−6.4% Ir, fast −4.2%/−7.5%/−6.1% (json/text/skewed), balanced −6.1%/−5.9%/−0.6%, opt/ultra ≤0.1%.
- output bitstream side: u64-spelling bit writes (see the encoding page); final ratio json 6.15 (vs zstd-1 6.11).

## Fast (dfast, counterpart of libzstd level 3)

- **mis-tiering lesson**: Fast initially used chain+lazy (zstd-3 is actually dfast) — a 2.5MB hot randomly-accessed table + per-position insertion + lazy's doubled search; json lagged 2.73× and text was 3× slower than Fastest. After the dfast port, json +80% (175→314 MiB/s, ratio 5.47→5.33 overtaking zstd-3's 5.31), text +154%. `19077f3`
- skeleton: dual tables (hash8 2^17 prime 0xCF1BBCDCB7A56463 + hash5 2^16 reusing the chain buffer), insert-then-probe, two-position pipeline, ip+1 long-probe upgrade after short hits, backward catch-up, repcode ip+1 pre-probe, **zero table insertion inside a match**, 4-anchor backfill into both tables after a match + immediate repcode loop.
- **emission path slimming**: `SeqWord` 16B single stream (codes/add_bits/add_nbs three streams into one, 3 push→1 push; push/pack must be `#[inline(always)]` — with plain #[inline] it stays uninlined and still costs 6.8%); ll==0 sequences (50% of json, rep chains) skip the literal copy; probes become cmovs. json 314→366 MiB/s. `1398d23`
- **stateless miss step** `1 + (ip-anchor)>>8` (drops the per-256-jump counter pair) + exact backfill predicate ("backfill only when the match covered the probe position", replacing the step<4 proxy): json +1.7%, text +2.6%. `0b46f21` `06b67dc`
- **two-phase scan loop + `inline(always)` on `rep_chain`**: the same seeded/steady split as the fast strategy (see the Fastest section); this loop's live set is even larger (two tables, two hash logs), so the dead weight cost more — gungraun fast json/text −5.7%/−5.4% Ir, skewed −8.1%, random −5.7%; wall json.fast 371→387 MiB/s (x1.29→1.25 vs zstd-3), text.fast 10821→12033, skewed.fast x1.37→1.31.
- **distance-resolve + idx-space rep probe (2026-09-11)**: the same two rewrites as the fast strategy's steady-body slimming (see the Fastest section) land bigger here — the dfast body carries two tables and two resolves per position. gungraun fast json/text −9.7%/−8.4% Ir; wall x1.22-1.25 vs zstd-3 (was 1.25; between-run drift is ±5%, the Ir cut is the solid part).
- window 1MiB→**2MiB (W21, 2026-09-12)**: libzstd's L3-9 all run wLog 21, and on large real binaries the window — not the matcher — decides the ratio. Control experiment on the 100MB ELF-concat corpus (`bench/gen_big.sh`): libzstd-3 capped to wlog=20 lands within 0.03% of our old 1MiB output (42,050,022 vs 42,063,166), i.e. same-window our dfast was already at parity; the 2MiB window then takes both sides forward — dll fast 42.06MB→30.19MB (−28%, and 8.1% *denser than libzstd's own L3* at 32.86MB) while running +39% faster (236→329 MiB/s; longer matches shrink both the scan and the literal stream). Corpus: json ratio −1.2% (6262491→6339383, now exactly libzstd parity — both use W21), text/skewed bit-identical sizes, speeds json +4% (387)/text +11% (12045)/skewed +12% (183); the pre-u32-tables falsification (json −1.1%, −4% speed) did not reproduce under the current matcher.
- dll-shaped corpus facts for future A/Bs: avg_ll 3.58 vs json 0.72, avg_ml 10.9 vs 15.3 (literal-heavy short-match shape); L1-load-misses 1.72/B vs json 0.79/B (near-uniform hash spread — table probes stop hitting L1); at matched windows the residual speed gap to libzstd-3 is x1.35 (359 vs ~480-560 MB/s, after the emit inline below). Instruction-side decomposition (callgrind dll32, 2026-09-12, vs the zstd CLI's `ZSTD_compressBlock_doubleFast` with storeSeq inlined): the miss-loop bodies are near-identical (~45 vs ~47 inst/iter at the same `1 + run>>8` step — the earlier "3× more scanned positions" reading did not reproduce; nseq/avg_ll differ because our output is denser); the excess was (a) `DfastEmit::emit` at ~170 Ir/seq — outlined (8-arg call, rep via `&mut` memory, Vec fields loaded through self, unprovable-order sub checks) vs libzstd's inlined storeSeq+anchors — **landed 2026-09-13, see the next bullet**; (b) the literals pipeline, whose huff0 stream half is now closed (dual-accumulator port, see the encoding page). We conversely win 2× on encode_sequences (74.6M vs 158.1M Ir). Wall on this shape is cycle-parity with the CLI's compress worker; the CLI's headline number pipelines I/O on a second thread.
- **`DfastEmit::emit` inlined into the scan loop (2026-09-13)**: `#[inline]` → `#[inline(always)]`, the same treatment `rep_chain` already documents (the phase-split macro instantiates call sites twice, halving the inliner's budget per copy — plain `#[inline]` flips to an outlined call in the steady phase). The calling convention itself was the tax: three stack-passed args, rep round-tripping memory, Vec ptr/len/cap loads through `self`, prologue/epilogue — ~50 of the outlined body's 170 Ir/seq over 1.21M calls (26% of the whole fast encode on dll32). Inlined, the seq push and anchor writes fold into the loop like libzstd's storeSeq; no layout lottery materialized (all four shapes improved). Byte-identical output; gungraun fast: json −8.2%/text −7.5%/skewed −1.3% Ir, fastest tier bit-for-bit unchanged (`TableEmit::emit` was already `inline(always)`); interleaved wall dll100 335→359 MiB/s (x1.47→x1.35), json 386→421, text 11055→11616, skewed 184→199; balanced/best/opt ±1% (their `emit_chain` was already inlined — no separate symbol at level 6).
- **zero-add-bit fast path in `pack_seq` (2026-09-13)**: LL codes 0-15 are ll itself and ML codes 0-31 are ml-3, both with zero add bits, so `ll < 16 && ml < 35` degenerates the whole pack to `bsr` + ors — no LUT+META load pairs, no variable-shift add merge (LLVM builds the `(1<<log)-1` mask as `0x80000000 >> log; dec`). Coverage: json.fast 99.997% of ll / 96.5% of ml; dll-shaped avg_ll 3.58/avg_ml 10.9 sits deep inside; text's 557+ avg_ml sits outside but emits per MiB are ~30× sparser. skewed's ll<16 share is only 63.5%, yet branch-misses measured exactly equal (6.89M both builds) — the gap sequence is locally regular enough to predict. Byte-identical output (full-ladder dump); gungraun: fast json/text −4.5%/−4.2% Ir, fastest −1.7%/−2.1%, balanced −0.3%/−0.6%, skewed/random/zeros flat; wall within noise everywhere re-measured (json 431, dll100 358-363, skewed perf-stat cycles −1.2%) — the fast tiers' wall on the 32MiB shapes stays branch/latency-bound, the cut is for literal-volume shapes and drift-free machines.

## Balanced / Best (hash chain)

- **gain-aware lazy walk (libzstd lazy port)**: lazy positions compete on `ml*4 - highbit(offset+1)` (reps price 0) instead of raw length, a rep0 probe rides each step (`mlRep*3/4` gain forms), and the walk advances while improving with one second-chance probe at depth-2 margins (+7) — pure-length comparison had kept far chain candidates whose offset exponent cost more than the length saved, the root of the text.Balanced deficit. json 6.08→6.55 (+13.8% vs zstd-6), text 361.4→366.3 (deficit −2.35%→−1.05%); sequences drop (json −11%). Cost: the second-chance search adds ~30% matcher instructions on rep-dense json (149→120 MiB/s); the depth-2 margin itself is load-bearing (depth-1-only collapses to json 6.18/text 361.5), and the depth-0 rep bias stays `ml+3 > best_len` (more rep-biased than C, kept).
- **literal-cost-aware lazy walk**: the walk's gain comparisons (rep probe and chain probe) price a candidate's displaced literals at the fed-back code lengths (first four bytes — every candidate is ≥ MIN_MATCH — clamped to 6 bits: the walk is a *local* selection and uncapped 11-bit prices let cap-priced bytes dominate whole walks; clamp sweep on balanced bulk-st json 4726875/4701990/4697420/4725425, text 91243/91232/91200/91140 at none/8/6/5 — the json swing dwarfs the text one at every step) instead of the flat `ml*4` scale; at default lengths both formulas reduce bit-for-bit. Cheap-reject gain caps (≤6 bits/byte) skip the gathers when even the best case cannot beat the incumbent. json.balanced 6.66→7.14 (+15.7%→+24.1% vs zstd-6), text.balanced flat (368.07→367.92, −0.57%→−0.61%), the other 104 ratio cells bit-identical. Cost: better pricing accepts more walk steps on json, +13% matcher instructions (json wall 119→~106 MiB/s, still ×1.72 ahead of zstd-6) — same exchange pattern as the lazy rework (+7.7% ratio for +30% instructions), better rate.
- **literal-cost-aware store gate**: the block encoder feeds the Huffman code lengths of each block's literal table back to the matcher (`Matcher::note_literal_costs`, per-frame/job reset keeps MT output content-deterministic), and the chain gate stores a match only if the displaced literals — priced at those code lengths, uncovered bytes at the 11-bit cap — cost more than `highbit(offset) + 7`. The flat 4-bit constant traded json against text monotonically (+4/+7: json 6.21/6.55, text 368.1/366.3); the whole swing is 5-byte matches at 8-32 KiB offsets, whose displaced bytes are nearly absent from text's hyper-skewed residual literal stream (the *average* residual entropy, ~0.2 bits/B on text vs 3.3 on json, anti-predicts the desired direction — the marginal code length is the right price). text.balanced 366.3→368.1 (−1.05%→−0.57% vs zstd-6) AND json.balanced 6.55→6.66 in one move; skewed (flat 4-bit alphabet) and random (no Huffman blocks, default lengths) reduce to the static gate bit-for-bit; speed neutral. Only the chain levels consume the feedback; the fast/dfast seed gates keep the static +7.
- position-indexed chain table + lazy (hash-log/chain-log/depth/lazy/window parameterized, a single `ChainMatcher` reuses emit/extend/repcode logic). `f8cc66d` Porting pitfalls: repcode backward extension must keep ≥1 literal; pos==anchor must probe rep (otherwise it loses to its own Fastest by 8×) — details in the pitfalls notes.
- **miss-run acceleration**: miss acceleration on incompressible runs (climbing in steps over long literal runs), random ~2.1 GiB/s at all levels, Best faster than zstd-12's 918 MiB/s. `47b60b0`
- **reach=window principle**: the chain table is position-indexed, so chainLog is the match reach; `reach<window` (C18/C19/C17) collapsed on skewed — long-distance repeats lost → matches shorten → position-by-position scanning slows. Balanced settled at W20+C20 (same 9MB table yet better everywhere: >1MB high-cost offset encodings eliminated). `3c88244`
- **broken-chain fix (major)**: insert used window indices while walk used absolute positions, so once win_base advanced, walks ran over truncated garbled chains (effective depth ~2-5) — Balanced/Best's earlier "speed lead" was an artifact of burning fewer probes, and the ratio was off too; the 4× collapse of streaming Best 18 vs bulk 74 MiB/s shared the same root. After the fix, the whole ladder was retuned on real chains + **beat-check** (a 4-byte beat check on candidates avoids full extension). `36203c1` `4ff2b7b`
- **Best core swap**: depth 16→64 bought only +0.9% ratio for a 2.7× speed difference — deep search has terrible cost-effectiveness, so Best switched to a low-config optimal parser (16 compares / targetLength 32). json Best 5.77→6.88 (overtaking zstd-12's 6.14), text 270.8 (overtaking 256.1). `b39a192`
- **table entries to u32**: store the low 32 bits of `abs+1` (0 = unwritten sentinel); on read the high bits are rebuilt from the scan position, wrapping on a 4GiB period; stale entries are covered by window-domain validation + byte verification as a backstop. Table working set halved (Balanced 16→8MiB, aligned with libzstd), json.Balanced +18%, text +20%. The epoch mechanism retired (the opt parser keeps its epoch u64). `327bc99` Comparison: with the Fastest 2^15 table (L2-resident), u64→u32 had no effect — **entry width is a lever only when the table exceeds L2**.
- **window 1MiB→2MiB (W21, 2026-09-12)**, chain table stays 2^20: positions beyond 1MiB alias in the position-indexed links exactly like libzstd's cLog-below-wLog chains (its L6 runs wLog 21 against cLog 18 — 8× aliasing), while the head table's newest-wins probe still serves candidates across the full window. Ratio: json.balanced 5516920→4711529 (**−14.6%**, +23.7% vs zstd-6 — the json corpus's tile repeats live at 1-2MiB distances), text 92833→91200, dll 40.41MB→28.22MB (−30%, 7.6% denser than zstd-6); skewed/random/zeros unchanged. Speed: dll +17% (72→84), skewed +9%, random +30%; json −14% solo (107→92 MiB/s — colder far candidates: L1-misses 1.57→1.77/B, instructions only +3.5%; the ratio win itself is real work spread over 2× the reach) and text −10% in the interleaved matrix; json x vs zstd-6 now 2.10 carrying a +23.7% density lead. C21 (8MB chain table, no aliasing) bought back only +5 MiB/s on json at dll-equal speed and +4MB/encoder footprint (×MT workers) — rejected. The old "reach=window" principle stands corrected: W4M-on-32MiB-corpus was the wrong test shape; what W21 needed was a corpus whose redundancy actually sits at 1-2MiB (large binaries, tiled json).
- **chain-walk search inlined + distance-resolved (2026-09-13)**: the `search` closure sat outlined at its two call sites (scan loop + lazy walk) and its calling convention was the tier's top hotspot — 66% of json.balanced cycles paid on 7 closure-env loads, ~12 stack round-trips, and a per-call runtime mask rebuild, on top of hashing and head-reading every position **twice** (search once, the insert block once). Now a module-level `#[inline(always)] chain_search` (the `DfastEmit::emit`/`rep_chain` precedent): the caller hashes and reads the head once, passes the entry in, and the insert block links the chain slot to that same value (nothing writes the table in between); the walk resolves entries as distances — `dist = pos - entry + 1` wrapping — with `dist - 1 < reach` admitting exactly [1, reach] and replacing the `unpack_pos` Option plus the separate candidate-floor compare (the u32-entry resolve rewrite the fast/dfast loops already took). One correctness trap on the way: a stale pooled-table slot (cross-frame residue) can hold `pack_pos(pos)` of the current position — dist 0, the candidate byte-compares against itself and `(idx-cand).ilog2()` panics; the old wrap check covered it implicitly, `dist - 1 < reach` restores the rejection (see the pitfalls page). Cumulative with the mask drop: gungraun balanced Ir json 134.6M→109.9M (**−18.4%**), text 64.3M→52.9M (**−17.8%**), skewed −1.8%; this change alone −13.0%/−12.7%/−1.3%, fast/fastest Ir bit-identical to the mask commit. Wall interleaved: json.balanced 80→87 MiB/s (x1.50→1.40 vs zstd-9), text.balanced 2637→2818 (x0.63→0.59); dll100 solo 96-97 flat. The perf profile after: the outlined symbol is gone, `start_matching_codes` owns 94% with everything inlined.
- **two-phase seeded/steady split of the chain scan loop (2026-09-13)**: the same macro split the fast/dfast loops already have — the job-start state (`seed_offset`/`seed_hits`/`seed_budget`, `rep_pending`) only winds down, so the steady instantiation constant-folds all four (plus the rep-gate branches) out of the body. Byte-identical (full-ladder dump); gungraun balanced Ir json/text/skewed −0.38%/−0.78%/−0.44%, random/zeros unchanged; wall flat on every shape (json solo 86-88, text 2981-3218, skewed 1933-1961, dll100 106-107; interleaved 87/x1.395 and 2826/x0.598, at parity with the recorded 87/2818). Kept for structure and the deterministic Ir cut, but it **falsified the spill-relief theory**: the four live values were supposed to be why the walk's params (win_base/pos_abs/reach/depth/mask) sat in stack operands — removing them only reshuffled allocation. Post-split profiling closed the model: cycles AND L1-miss samples concentrate in the same two steady walk copies (**82% of cycles, 93% of L1 misses** on json 32MiB), the instruction-level profile is flat (hottest single instruction 2.5%, the old "~7% beat-check loads" concentration died with the outlined closure), and ~66 cyc/walk-step ≈ one serialized L3-class load — the walk is a **latency-bound chain-link chase** (4MiB chain table + beat-check reads at 1-2MiB candidate distances), the per-step stack operands hide under the load latency. Ir-side work on this loop no longer converts; the remaining levers are latency-side (see todo 5).
- **cross-position pipelining of the lazy walk's hash+head read (2026-09-14)**: each chain search paid one more serialized L3-class load — the head read — in front of its walk. The scan body now issues the pos+1 hash+head before the incumbent walk (the dfast ip0/ip1 pattern); the lazy walk consumes it at the first search and each search refreshes for the next under the walk's shadow. Two invariants carry the correctness: no table writes happen inside the lazy walk (a pre-read cannot go stale), and every path to the next search steps exactly one position (the refresh is always the right one; its guard equals the next attempt's break condition, so a skipped refresh is never consumed). The scan-body insert's newest-wins write is the one exception, fixed up on a slot collision (`ph == h` → `pack_pos(pos)`); the depth-0 rep probe advancing pos (first search at pos+2) and the block tail fall back to fresh compute. **Issue placement is load-bearing**: the same pre-reads issued after the incumbent walk (gated on the lazy walk actually running, killing long-match waste) kept only +0.5% dll and flipped json to −2% — loads placed after a loop whose exit branch predicts poorly decode behind it and lose the shadow; OOO overlap does not rescue bad issue placement across a data-dependent loop exit. A dual pre-read (pos+1 and pos+2, covering the rep-advance case) took dll +4.5%/json +2% but cost text −2.5% wall from the scan-body code presence alone (gating the waste off did not recover it — layout); the landed single pre-read keeps dll +4.5% (105-107→110-113 solo), json +1.5-2% (89→90), text +1.4% (3251→3295 6-pair solo; interleaved matrix text +2.5%), paying skewed −2% (the wasted loads on its long-match iterations: +18% RAM hits at +0.5% Ir). Ir is up json/text +2.6% — the issued-early loads are the cost, the hidden latency the pay; a latency-side lever exactly as the walk model ordered. Byte-identical full-ladder output.
- **gungraun's 1MiB slice under-measures the chain tiers (2026-09-13, model input)**: json.balanced measures ~100 Ir/B on the slice but ~463 Ir/B on the full 32MiB file (4.6×) — the 2MiB window never fills in 1MiB, so walk depth and the far-candidate regime barely appear; Ir deltas on chain tiers validate instruction-count changes only, wall conclusions need the full corpus (`prof`/`matrix`). Corollary: the chain-walk rework's −18% Ir bought 87 vs 80 MiB/s json wall, and the split's −0.4..−0.8% bought nothing — the conversion rate was set by the slice/full-file regime gap all along.

- **cold-start DUBT head (2026-09-15)**: row 9's frames parse the first `HEAD_LIMIT` (1.125 MiB, 9 blocks) through the btlazy2 driver before the chain takes over, closing the text.Balanced deficit (todo 9): the whole deficit lived in the first cold-start tile, where the chain's newest-first selection accepts nearer-shorter candidates (ml 15@212 vs the tree's 18@809) — exactly the span where the DUBT tree's oldest-first order wins, and the chain parses at parity after it. ## Best (btlazy2, counterpart of libzstd levels 13-15)

- **u32 entries + the skewed.best cost model (2026-09-15)**: the stubborn x2.87 skewed cell is a memory-footprint artifact, not an algorithmic one. Taint-free attribution (perf + instrumented event counters on the 32 MiB corpus): 83% of cycles sit inside `find_all_matches` at IPC 0.44, with 200M L1-dcache and 100M dTLB load misses per pass over a 96 MiB ring+heads working set — the u64 entry form doubled libzstd's 48 MiB (U32 `chainTable` + U32 `hashTable`). The event table per pass: 19.4M searches, 14.1M filled, 12.5M chain-walk steps and batch sorts (26.4M sort descents), 49.8M sorted-descent steps, 76.2M `count_from` calls averaging 4.5 verified bytes — ~460 cycles per tree visit, i.e. a serialized ~DRAM-latency load per step while the compares themselves are trivial (16-symbol data makes every 5-gram bucket ~14 entries deep, so every search walks and sorts a backlog). The port truncates positions to u32 and rebuilds them against the scanning position (candidates are window-bounded, the high bits are implied; a stale entry from an earlier 4 GiB period rebuilds as an in-window phantom that dies on the range check or the byte verify — the same accepted class as the chain tables). `POS_BIAS` stays 0: position 0 reads as the null link and 1 as the unsorted mark, the identical sentinel collisions the u64 form carried, so the full-ladder dump stays byte-identical; a +2 bias (libzstd's `ZSTD_WINDOW_START_INDEX` reservation) measured +543/+97/-224 B on json/text/skewed and was not taken. Best-tier footprint halves to 48 MiB (×MT workers). Measured solo perf-stat on skewed: cycles 41.2G→26.3G, dTLB misses 99M→62M; interleaved matrix skewed.best x2.865→x2.16-2.22, json.best x1.627→x1.38-1.50, text.best x1.184→x0.82-0.94 (ahead of libzstd for the first time).
- **literal-scale hoist in the btlazy2 selection (2026-09-15)**: every candidate of one search prices its length against the same four `lit_lens` bytes (the position is fixed), but `lazy_value` re-gathered them per candidate behind the matches-array loop and LLVM does not hoist that. Split into `lit_scale` (per position) + `scale_value` (per candidate): driver Ir 4.50G→3.48G on skewed (-23%, against libzstd's 1.12G for the same events — the remainder is the literal-aware pricing itself, the +2.5% density mechanism), whole-encode Ir -8.2%; output byte-identical.
- **DUBT finder (2026-09-14, `encoding/dubt.rs`)**: a faithful port of libzstd's doubly-unsorted binary tree (`ZSTD_updateDUBT`/`ZSTD_insertDUBT1`/`ZSTD_DUBT_findBestMatch`), replacing the retired shallow-insert architecture below. The fill pays **three stores per position** (hash-head update, chain link to the previous head, unsorted mark) with zero compares; sorting amortizes into the searches — a search walks its bucket's unsorted chain (reversing slot[1] into a backtrack link), nullifies the chain's far end (libzstd's deliberate ratio-for-speed cut), batch-sorts the walked nodes oldest-to-newest with one budgeted descent each, then descends the sorted tree collecting strictly improving candidates (C returns one best; our literal-aware selection consumes the whole improving set, worth ~+0.5% over zstd-13 at equal knobs). Match interiors and stepped-over positions never pay beyond the fill — that is the entire speed point over a fill-time-sort tree.
- slot discipline carries the soundness: `[0]` is the chain link while unsorted and the smaller child once sorted, `[1]` the mark and the larger child; children are always older than their parent and every sorted node's slots were written by a completed descent, so a descent never crosses an unsorted node. Our `UNSORTED` sentinel is bit 63 (positions stay < 2^47), so unlike C's value-1 mark it can never collide with a real entry. Entries are raw positions (no epoch tag): job prefill clears the heads only (the strip fill rewrites every ring slot — strip = full window = full ring), and the per-frame reset clears both tables.
- **the collection cap must be block-scale, not the row's targetLength**: an early-out at `sufficient_len` (32) stops the descent's threading with the walk, and on match-rich data the tree starves — the tiny-vocab ladder synthetic collapsed to 28110 B (vs L9's 24142) until the cap moved to `OPT_NUM` (4096) like the optimal parser's own walk: 19390 B, past even the old Keep-retention rescue (22761). json moved 5472046 → 5364906 the same edit.
- **lazy2 selection loop** (port of `ZSTD_compressBlock_btlazy2`): each position's repcode and tree candidates compete on value-minus-offset-price, a two-deep lazy walk chases a better start under libzstd's alternating margins ((rep x3, +1, +4) then (rep x4, +1, +7)), literal-offset matches backward-extend into the pending literals, and the offset-2 chain follows every emission. Replaced the tier's old low-config optimal-parser rows (json x4.22/skewed x6.22 — an algorithm-class mismatch).
- **literal-aware lazy margins** (the chain tier's measured win, ported): displaced literals price at the previous block's fed-back huffman code lengths (`lit_value`, clamped to 6 bits/byte; flat 4 bits before the first feedback = libzstd's raw `ml*4` scale bit-for-bit).
- retired with the DUBT port: the 2026-09-13/14 shallow-insert architecture — the opt tree with a split `insert_log` budget, `FillTerm::Keep` link retention and the STALE/taint recount machinery (the tiny-vocab ladder rescue). The DUBT tree beats the rescue outright (19390 vs 22761 B on the synthetic); the one measured loss is json's retention edge (ratio 6.27 → 6.25), traded for +24-52% tier speed.

## Opt / Ultra (optimal parser, full port of libzstd zstd_opt.c) `c726dfd`

- lazy-filled binary match tree (insertBt1 / insertBtAndGetAllMatches, epoch tags absolute positions); forward DP over stretches + fixed-point fractional bit prices (×256, highbit+linear interpolation approximating -log2(p)); cross-block frequency adaptation (rescaleFreqs decay + updateStats); btultra match+1-literal recheck; 2-pass first-block statistics seeding (the epoch bump invalidates the pass-1 tree).
- correctness-critical details: `ZSTD_count` returns a pointer difference (continuing a count must **replace**, not accumulate); rep history is updated **once per series** by the path traversal (per-sequence updates on the emission side are the decoder-equivalent semantics; pick one); tree-insertion counting is capped at 4096 within the DP window — otherwise regions skipped by the parser (long matches at far offsets) get recounted from stale heads, text 45→313 MiB/s.

## Tuning lessons (general across levels)

- **ratio is tightly coupled to table pressure** (Fastest): any change that raises insertion volume (full-density probing, slow ramp) crashed the json ratio (down to the 5.5 tier); only after dual anchors cut long-match insertion volume to 1/8 did table pressure gain headroom.
- **depth has terrible cost-effectiveness**: json d16 vs d64 is only +0.9% ratio for a 2.7× speed difference. The road to high-end ratio is the opt parser, not deeper chains.
- **the hash table must match the data**: on skewed (16-symbol alphabet) H17 has ~256 chains per slot that can never be fully walked, H20/H21 terminate at chain tails (zstd-9 is H21); H18 instead collapses on skewed (finer head buckets → chain-head hits thin out).
- **locking periodic corpora relies on direct rep0 probing, not the hash table**: a fixed grid is mathematically hopeless on clustered 5-grams (twin slots with equal values recursively burying each other / phase-alignment traps) — hence the MT job-start seeding mechanism.
- **gain gate** (store decision): C's +7 is a "replacement gate", not a store gate; our tables are denser than C's (stride-1 prefill + walk takes the longest), so the selection bias toward weak long-distance matches is larger and the gate is deliberately stricter. The flat `ml*4 ≥ ilog2(offset)+7` form false-killed short/medium-distance matches on text (-0.55% at T=7) — resolved by pricing the displaced literals at the previous block's Huffman code lengths instead of the flat 4 (see the Balanced section's store-gate entry).
- **W4M is a double loss** (32MiB-corpus shape; superseded as a blanket rule by the W21/W22-23 landings): a window only finds more distant matches, not longer ones — bare widening wins exactly when the corpus's redundancy sits inside the added reach (dll's 1-8MiB, json's 1-2MiB tiles); for farther distance classes the carrier must be LDM, not the window.
