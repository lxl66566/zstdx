# Pitfall Log · Engineering and Benchmark Methodology

## Noise and criteria

- **Sequence-dump walks must anchor on executor truth, not on wire values + block tiling**: reconstructing absolute positions by tiling (ll+ml) from block starts and resolving repcodes by hand mis-assigns any sequence whose end coincides with a block end (greedy `end <= be` pulls the NEXT block's first sequence in), and on repetitive data (json) thousands of mis-resolved matches still byte-verify against the output by coincidence — the error surfaces megabytes later or never. Record (match_pos, ml, offset) at the executor and cross-check; a byte-verify gate alone is NOT sufficient validation of such a walk.
- **Analysis pieces must be cut at the ENCODER's real job boundaries** (`mt_job_size_for`, printed by `emitframe`): a uniform guess drifts whenever the input is not divisible by 2×workers (32 MiB json: jobs 4,194,316 B vs a 4 MiB guess), and every misaligned cut manufactures depth-guarantee "violations" from legal mid-job shallow reads — including an entire phantom tail piece when the last job is short. Streaming's unpledged growing grid (epoch-doubling, finish-time tail split by worker count) is not recoverable from the frame at all.
- This machine (Zen4 32C) has ±10% noise with a **slow-drift phase**: mornings stable at ±1%; in the afternoon the same binary can be 25-50% slower. Cross-time-of-day conclusions count only as git-stash back-to-back same-machine A/B; every single bench must be re-run a second time.
- random's bimodality (1388↔2027 MiB/s) is frequency drift (lscpu scaling 73%) + SMT sibling scheduling; skewed.Fastest readings are heavily affected by the sibling core and settle back after one re-run round.
- **Deterministic output sizes are the only free, trustworthy A/B signal** (for changes that should not alter output); speed conclusions need multi-round medians or in-process toggles; "gains" within ±10% in a single round are untrustworthy. bench_matrix's x factor drifts ±10% across runs (even unchanged cells drift).
- Bench position bias: within one test, the binary that runs later consistently gets a 4-5% advantage (cache/frequency phase) — A/B must be position-aligned (alternate first/second, compare by position).
- **Allocator cross-contamination**: when serially running multiple impls/sizes in one process, zstd-side CCtx allocation churn shreds the malloc arena → subsequent timed segments distorted 3× (random-64K serial ~3000 vs 9200 in a single-shape process). Small-load criteria must pin IMPL+SIZE to a single-shape, single-size process.
- glibc's dynamic mmap/trim thresholds drift with the allocation sequence: pinning `MALLOC_TRIM_THRESHOLD_` actually disables zstd's adaptivity (its random-64K collapses 3×); for small corpora, either pin it or run isolated.
- The first run after a build disturbance can read falsely low by 30%; take final numbers from multiple stable rounds.
- In solo bench, in-process cell order is a source of allocation-layout artifacts (a table's size change moves where subsequent allocations land); decide A/B with fresh processes, or at least cross-validate across two environments.
- BMI2 dispatch overhead is Zen4-only data (measured neutral zero-cost); re-measure on Intel before generalizing dispatch conclusions.

## cargo / git

- **A/B always runs back-to-back on the same machine via `git stash`**; after a stash round-trip `target/` is not rebuilt automatically — once spent half a day objdumping the stale BASE binary analyzing "bmi2 not generated".
- **`git stash` operates on the SHARED stash stack, not the worktree's**: all worktrees of this repo (zstd-rs, -dev, -dev2, -dev3...) push onto one `refs/stash`, so a `git stash pop` after any delay can restore (and drop) ANOTHER session's WIP — observed live: a pop restored a foreign match_generator/opt.rs diff and dropped its entry. Before popping, verify the top entry's content (`git stash show --stat`); on a wrong pop, the dropped commit usually still exists and `git stash store <sha>` re-registers it exactly. For worktree-local parking prefer scratch commits on the branch (`git add -A && git commit -m wip`) and reset later.
- **cargo A/B binaries are per-package**: `cargo build -p zstdx` does NOT refresh `target/release/zstdx-bench`; rebuild the bench binary after every edit (a ratio run once showed byte-identical output — it was a stale binary).
- On this repo's git version, `git stash push --staged` only copies without restoring the scene; for splitting atomic commits use `git restore --staged` + `git commit <path>`.
- **cargo fmt touches historically unformatted files**: before committing, `git checkout --` the unrelated files (nearly dragged 6 unrelated files into an atomic commit).
- `cargo build --no-default-features` has a caching illusion: touch sources to confirm recompilation before counting warnings; it also recompiles examples as no-std and **overwrites the default build under target/release** (AVX-512 kernels cfg'd out, xxhash gone), invalidating all subsequent measurements — before measuring, rebuild the default build and verify with `nm ... | grep <kernel symbol>`. The no-default check must carry `-p zstdx` (a root build lets cli bring the hash feature back). (examples have moved out of zstdx; this risk is gone.)
- **`cargo test`'s piped exit code is tail's**: with `cargo test | tail`, cargo failure is swallowed by the `&&` chain while the success marker still prints. The test gate must be `cargo test > log; echo $?` — persist to disk and check the exit code and FAILED count; `2>&1 | tail -N` also truncates the output file to its last N lines (wasting a re-run round).
- **The debug test suite is a mandatory gate** (release all green ≠ bug-free); if the suite seems hung, first suspect "some panic poisoned the thread pool" (MT worker panic → join waits forever, 17 minutes of zero output); localize with `--test-threads 1` + running the test binary directly.
- Running the test binary directly requires the crate root (13 corpus tests use relative paths).
- The bench corpus is not in git (untracked generated artifact): copy it before benching in a worktree.
- Debug panic / eprintln instrumentation must be deleted before committing (one was once left behind; eprintln under `#[cfg(feature="std")]` compiles into release with the default feature).

## perf / attribution

- `setarch -R perf record` (ASLR off) + `perf script` to extract an IP histogram + objdump the corresponding address ranges and read them manually; **`perf annotate --stdio` output mixes in kernel disassembly and is untrustworthy**.
- **An annotate window too large (+0x1000) counts in neighboring symbols** (FSETable::clone was once mistaken for instructions inside emit_match); get exact addresses with `nm` first, then use a small window.
- AMD branch-miss event sampling skid: attribute via stub bisection + perf stat totals (details on the decoding pitfall page).
- **Instruction-count criterion**: late in optimization, ±5-25% wall-clock swings from single-line changes are usually layout/scheduling noise; only a drop in `perf stat` instruction count is a real gain; flat instructions + wall-clock swing counts as ineffective disturbance. Micro changes: instruction counts; end-to-end changes: interleaved wall-clock medians.
- LD_PRELOAD counting memcpy/memmove: the sharp tool for locating small-copy disasters (json 32MiB ~3M PLT calls).
- **Register-pressure law**: at ≥15 live values LLVM keeps the bit window on the stack; 12 values can stay in registers (a `shlx` with a memory operand in annotate means you are hit); removing a single memory operand is nearly useless (+0.2%, the out-of-order engine already hides memory latency), shortening dependency chains only +1%, **cutting serial dependencies (grouped batch extraction) pays the most**.

## Toolchain / environment

- WSL: `stat /mnt/c/...` random I/O errors (statx acting up, cargo/git dead across /mnt/c) → read file contents via cat/pipes; **WSL reading large files on /mnt/c can hang the entire VM** (recovered with wsl --shutdown); keep the analysis environment on native ext4; WSL auto-shutdown on idle wipes /tmp (put artifacts in ~); `wsl -e` errors on empty args and nested quotes break — write complex commands as .sh and run `wsl bash <path>`.
- The Windows side has no grep/sed/head -c (use rg/powershell); `find` is Windows find; `;` is not a command separator in cmd; powershell bulk -replace: watch the `` `n `` escaping and regex collateral damage (as_ref was once replaced along with the target).
- Three pitfalls of parsing zstd frames with python: in `(b1<<8)|b2+0x7f00`, `+` binds tighter than `|`; the literals-header size-field bit width misremembered; `sort -rn` mixed in kernel symbols. **Before writing an analysis tool, check its field definitions against a known-correct decoder.**
- tar extraction should use the default (it overwrites); `--skip-old-files` skips already-existing files — this once kept the WSL side running old code.
- Background task output: avoid tail/head in pipes; persist the full output to disk, then grep.
- gungraun comparisons need explicit `--save-baseline=X` / `--baseline=X`; the default "No change" compares the run against itself. Baseline names reject `-` (use `_`).

## Corpus and reproducibility

- **The corpus is not comparable**: gen_corpus.sh's text.raw flattens the src tree — any src change changes the corpus; historically text's two shape phase transitions (the cross-tile match unlocks at ratios 299.6 / 239) both depended on the repeat period landing inside the window range; once src bloats past 768K the shape will collapse again. **Consider pinning a tar snapshot.**
- Cross-session absolute-value drift: l6 json read 171-179 this session vs 177 recorded last round — rolling match_generator back to the previous version gave the same readings, confirming no regression. **For cross-comparisons trust only same-session A/B.**

## Editing tools

- The Edit tool matches by text: identical tail context in the X1/X2 functions caused edits to the wrong function — when editing similar functions, old_string must carry an identifier unique to each.
- Match-arm edits: old/new should contain only the target arm (once copied the next arm wholesale into new_string, producing a duplicate arm exposed only by clippy's unreachable pattern — behavior happened to be correct but redundant).
- After batch-restoring code, verify with `git diff` before benching: a python replace missed one site (`replace(pat, 2)` hits only the first two), json.fastest size drifted -101B, caught only via deterministic size comparison — **diff first after every change; deterministic sizes are a free regression probe**.
- Sweep scripts: a regex replacement dropped one comma so a subpattern never matched — one "unchanged" run yielded a "changed" conclusion masked by another configuration's data. **Parameter sweeps must print back and confirm** (set_lvl.py echoes + asserts).
- Bench-tool self-inflicted wounds: the mibs formula forgot to multiply by rounds (`raw.len()/elapsed` ≠ `raw.len()*n/elapsed`); a filter-argument substring mismatch silently runs an empty process (utime≈0 is the signal); the x factor's `%.3f` is unreadable at extreme values (look at the MiB/s column); zeros is a free noise-calibration cell; seqstats hardcodes `Level::Fastest` — useless for non-Fastest work (a `--level` flag is the real fix).
- **Dev features must never ride the bench crate's default dependency**: the `seq_dump` decoder hook (a TLS `Vec::push` per sequence inside `decode_step`) was enabled unconditionally in zstdx-bench's zstdx dependency for the `seqstats` tool — every measured decode (and every ratio-sweep roundtrip gate) silently ran with it: json stream 1733→1224 MiB/s (−29%, x1.26→x1.79 vs libzstd) while the zstd side was unchanged, so the A/B harness itself reported a phantom regression. The interleaved A/B protects against clock drift, not against a one-sided build difference. Rule: instrumenting features in the measured crate's hot loop are bench-crate opt-in features (`--features seq_dump`), and after landing any instrumentation hook, re-run one timing cell at HEAD as a canary before trusting later numbers.
- **sed no-ops disguised as A/B data**: a margin sweep `s/+A/+B/` silently no-ops when the pattern is absent — an entire sweep step (and any test rerunning the same value) then measures the unchanged file. Verify the file actually changed (grep) or use python asserts; two bogus "identical output" conclusions were drawn before detection.
- **A global `core.fsmonitor=true` swallows file changes written by tools**: after a python script/cargo fmt modifies files, the fsmonitor daemon does not report it → git believes the files are "unchanged" (the blobs actually differ) → status shows no dirty and pathspec commit silently commits old content (once lost all source changes in a fix commit, exposed only when `git show --stat`'s file count did not add up). **In this repo run all git commands as `git -c core.fsmonitor=false`, and always check the stat file count after committing.** Knock-on: pathspec commit resets the index to HEAD+committed paths, so a previously staged `git mv` rename falls out of the index entirely; files ignored by .gitignore but historically force-tracked (fuzz artifacts) must be re-staged with `git add -f`, otherwise the rename gets committed as a pure deletion.
