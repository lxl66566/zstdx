# Pitfall Log · Encoding

## Frame format

- **The per-block emission contract is "one reserved 3-byte header per block, patched by the caller" — any path that emits MORE than one block must take over header ownership explicitly.** The block splitter hit this twice in bring-up: (a) later partitions computed their header offset as `len - 3` *before* appending their own reserved bytes, patching into the previous partition's tail; (b) worse, the caller then re-patched the first reserved header with the summed size, producing a *super-block* header that swallows the partitions' own headers into its bitstream — our own decoder roundtripped it (permissively) while libzstd flagged corruption. Interop through the zstd crate is the mandatory gate for any multi-block-per-parse path; a `SplitOutcome::{Emitted, Single}` return now marks "headers already final and size-guarded" so the caller skips patch and checks.
- **Block size is capped by the declared window** (RFC 8878: Block_Maximum_Size = min(window, 128K)). The srcSize adjustment can never trigger this (window ≥ ceil_log2(src) ≥ src), so only a forced window log below 128K exposed it — libzstd rejected even all-raw frames ("Data corruption detected", error 36) while our own permissive decoder accepted them. Every emission path now reads `Matcher::block_size`; when adding any window-shaping knob, grep `MAX_BLOCK_SIZE` in emission paths first.
- **A wire-flag match arm transposed from the spec table leaves a dead arm and a panic on one size class only (2026-09-19)**: the FCS flag mapping read `3 => 8` where `find_min_size` yields 1/2/4/8 — the intended `8 => 3` — so every FCS ≥ 2^32 hit the panic arm: MT's fixed `frame_content_size: Some(src.len())` (any > 4 GiB-1 input) and a stream pledged at 2^32+. All smaller classes behaved, so every ordinary test passed. Spec-table mappings need boundary tests per class (255/256/64K/4G-1/4G), which pin the descriptor flag, the field width, and the decode roundtrip at once.

## Matcher

- **commit_space set the pos cursor to the block end → matcher fully idle** (all blocks degraded to pure literals), while rebuild-style unit tests kept passing — must be paired with skip_matching index-validity assertions and repcode emission assertions.
- After backward extension, the offset must use the final position difference `start - cand`.
- **After rep1_chain returns, `anchor_idx = ip_idx` is mandatory** (in all three emission paths), otherwise the chain-covered region gets its literals counted once more by the next sequence → decode TargetTooSmall (this line was lost once when porting from the old fast code).
- In the chain loop, repcode backward extension must keep ≥1 literal (floor=anchor+1): at ll=0, of_value 1 is rep-swap semantics (the ll==0 branch of `do_offset_history`); periodic data is guaranteed to blow up.
- In the chain loop, not probing repcodes when pos==anchor loses to our own Fastest by 8× — must mirror fast's probe=pos+1 semantics.
- **Index-domain split (major lesson)**: chain-table insert used window indices while the walk used absolute positions; the two agree only when `win_base == 0`; once any real driver (streaming compaction, bulk per-block adopt, MT job base) advances win_base, the walk runs entirely on truncated, tangled chains (effective depth ~2-5) — the "speed lead" was an artifact of burning fewer probes, the ratio was off too, and the 4× streaming collapse shares the same root cause. **(a) Streaming vs bulk output divergence is the smoke alarm for search-state divergence (the byte-identical assertion had previously only been checked for Fast/Fastest); (b) the index domain must carry the same invariant comment on both the insert and lookup sides.**
- Two pitfalls of u32 table entries (`327bc99`): for cross-frame stale entries whose value > pos with no 4GiB period to fall back through, `cand - 2^32` must be `checked_sub` (release wraps into a huge index and reads OOB — the first bench run carried the bug for a full round before re-verification caught it); the `!u32::MAX as u64` precedence trap (unary `!` binds before `as`, yielding 0; hi stays zero, silently). **Bit-manipulation helpers must come with round-trip tests across the 2^32 boundary.**
- **Non-determinism from not clearing u32 tables**: pooled state residue + a stride-3 grid writing only 1/3 of the slots → same input, same process, sizes jump between consecutive runs (json.Balanced alternating 5514733/5515064) — a latent hazard present since `327bc99`, previously masked by dense table filling. Fix: clear the head table per job (same as C); chain lists may be left uncleared (provable by induction: chain slots are only read at candidate positions, and candidates come only from cleared heads or this job's linked values). All alternatives were rejected: frame-epoch clearing (schedule-dependent), statically binding jobs (loses load balancing), tagging entries (pays on the hot path).
- **Raw-block fallback is a breeding ground for state divergence**: any cross-block encoder state (rep / reused entropy tables) must be reconciled against "what the decoder actually received" — a raw fallback must roll back rep + the reused table, otherwise the next block's Treeless/Repeat references a table the decoder never received.
- `ip1_idx - anchor_idx` underflow (the new anchor returned by emit can move past ip1): silent in release; the debug panic interrupts an MT worker → join waits forever. Fix: switch to an exact predicate with no subtraction.
- Matcher-scratch driver reproducing MT job scenarios: blocks must be ≤128K (ml>131074 hits unreachable), adopt_window only up to block_end (otherwise extend_match crosses the block and yields a huge ml).
- **A width mask written as a hex literal must be counted as live bytes, not digit groups**: `0x0000_00ff_ffff_ffff` is THREE zero bytes + FIVE ff bytes = 40 bits — one `ffff` group more than the intended 4-byte mask `0xffff_ffff`. The r13 dict-width cut carried exactly this typo and the "4-byte" hash silently stayed 5-byte: every per-knob A/B on top measured flat, a depth-only residue looked like the whole story, and a comment block full of (real) numbers pointed at a config the binary never ran. Diagnosed only by tracing fill-vs-scan hashes on a known 4-byte twin (`0a 23 20 74`) and recomputing the hash by hand. Width/bitmask constants need a byte-count comment next to the literal, and any "knob does nothing" result should trigger a does-the-knob-engage probe before it is believed.
- **A span gate without a slice is O(input), not O(span)**: the reach probe checked `head.len() < PROBE_SPAN` as its engagement gate but then parsed the whole `head` — the "fixed ~36 ms" probe cost 580 ms on a 33 MiB frame (json solo 76→41 MiB/s). The symptom (output byte-correct, speed halved) reads as a feature cost, not a bug; any prefix-probe pattern must slice `&head[..SPAN]` at the gate, and its cost claim must be re-measured on a large input before it is believed.
- **A replay cursor declared inside the read loop replays the same block forever**: staging probe bytes inside `FrameCompressor::compress`'s block loop reset `staged_read` each iteration — the same first block replayed until the frame hangs (32 MiB json stuck 10+ min, RSS 375 MB). Replay cursors live *outside* the loop they gate.

- **LDM gear arithmetic wraps by design**: the rolling gear hash is `(hash << 1) + GEAR_TAB[b]` over full 64-bit values — in C this wraps silently; Rust's debug overflow panic fires the moment LDM runs on large debug inputs (release was unaffected). Same class as the `fed` cursor: a shutoff gap must leave `fed` at the arm floor (`gear_rearm` semantics), or the next revival block's `debug_assert_eq!(fed, base)` fires and the canary split lands mid-match (a release-mode correctness bug, not just an assertion).
- **LDM empty-slot candidates need a split-side bound, not just the reach check (2026-09-17)**: `checksum_mask` selects an unwritten slot whenever the query checksum is 0 (the empty encoding also carries checksum 0), and its biased distance resolves to `split + 1` — inside the window reach for every split below the window size, so plain `split - dist` underflows (debug panic; release wraps and `extend_match`'s unchecked reads go OOB). All-zero windows never become splits (the gear over zeros settles at `-GEAR_TAB[0]`, which does not trigger), so checksum-0 windows are structured needles the fuzzer must craft — encode_stream artifact `crash-899d2f24` fingerprinted one; its 64 bytes head a split in any buffer they start (the checkpoint after a window is prior-state independent), which is the regression test's hook. Fix: `checked_sub`.
- **`asm!` lateouts may share an input's register — the template's own read/write order is the real contract (2026-09-17)**: `gear4_asm`'s template reads `h` after writing `c1`/`c2`, but `lateout` only promises "written after all inputs are consumed", so the compiler legally assigned a lateout to `h`'s register and `c3`/`c4` were computed from the clobbered value — dev-profile split sets diverged from the serial gear while the release fuzz build allocated differently (same source, different codegen, different splits; invisible to output gates because any split set yields valid frames). Fix: early `out` for `c1..c4`; `gear_feed_records_serial_splits` locks the inlined instance to the serial split set.
- **An empty holdout must skip scoring, not score zero**: the dict sweep calls `evaluate` even when the train/test split produced no test samples (a single small source) — the debug assert `!test_samples.is_empty()` fired under `--all-features`. When a sweep can collapse to one candidate, the evaluation step is optional, not unconditional.

## Entropy coding / bitstream

- **Rust operator precedence**: `1u64 << 62 / total` parses as `1 << (62/total)` (`/` binds tighter than `<<`), every normalization step wrong → ratio -28%. **When porting C's `f(a,b)`-style function calls, add parentheses manually.**
- **In the literals 5-bit size format, size_format occupies only 1 bit** (zstd spec: in the 1-bit form, bit3 is part of the size); writing it as 2 bits misaligns the entire rest of the block. For the Compressed type, sf=2/3 are 14/18-bit sizes (4/5-byte headers), a layout different from Raw/RLE.
- Packed-bitstream extraction must mask per segment: `(packed >> 8)` still carries the of field's high bits (up to 0xFFFF); you must `& 0xFF` before casting to `usize` — only a cast to `u8` makes truncation naturally equivalent.
- The three fields of `SeqWord.codes` are **FSE codes, not raw values** (ml is the ML code; ml-3 holds only when ml<15); decode diagnostics must use the META base or go through the reconstruction path.
- Three pitfalls of the FSE -1 symbol: the positive-probability sum of cross-check inputs must equal `table_size - count(-1)` (otherwise you generate malformed test inputs and false-positive); during SoA construction the -1 symbol is filtered out by `prob <= 0`, so its start state must be written explicitly at allocation time; the baseline packed into transitions (9 bits) requires baseline < 512, and widening acc_log must widen the packed width in lockstep.
- of_value semantics: non-rep match = offset+3, rep match ∈ {1,2,3}; when diagnostics print offsets, 307203 = 307200+3 — do not treat it as an independent constant.
- For pitfalls of parsing frame structure with python (nbSeq bit width, `+` binding tighter than `|`, sort mixing in kernel symbols), see [engineering methodology](workflow.md).
- **BitWriter hot-state handover carries up to 63 pending bits** — a batched writer that takes `hot_state()` and then reasons "my adds are ≤ N bits, the flush keeps nb < 48" must establish that invariant with one conditional flush BEFORE the first add: the entry `bits_in_partial` is unbounded (0..=63), so the first add can silently shift bits past the u64 top. `FSETable::write_table` lost exactly the high bits of its first description entries this way; the symptom surfaced far downstream (sequence-section underflow in `ramp_frames_decode_byte_exact`), not at the write site.
- **A table-coverage predicate must gate every site that emits the table, not just the main selection** (2026-09-19): after eaa6af23 put the predefined-mode bound on `FseTable::max_symbol`, two fallbacks in `select_from_counts` still returned Predefined unconditionally — the `nb_seq <= 2` basic shortcut (libzstd's `isDefaultAllowed && nbSeq <= 2`) and the normalization-corner fallback. libzstd wraps ALL its `set_basic` returns in `isDefaultAllowed`; porting a per-site decision without the surrounding gate leaves holes that are unreachable under today's window clamp but corrupt the moment it relaxes. Both now check coverage first; the corner's uncovered arm takes a flat one-state-per-symbol table (`flat_table`) instead — validity is the contract there, quality irrelevant.

## Memory safety

- **The reserve baseline is len, not the write position**: in bulk bit-write loops `pos` often runs ahead of `len` (set_len deferred to the end); `reserve(fixed value)` becomes a no-op once capacity suffices → later stores run out of bounds and corrupt heap metadata (delayed explosion as `realloc(): invalid next size`). Must use `reserve(pos + N - len)`.
- After the hash payload became u64, the scan tail guard (`block_end - pos < 8`) and the insert upper bound (`len - 8`) must be tightened in lockstep to avoid reading the uninitialized tail left by `set_len`.
- **The gated blocks' catch-up fill must carry the same HASH_READ tail margin as every other fill (2026-09-19)**: `catch_up_insertions` bounded its inserts at `block_start` (the gated block's end), but each insert hashes HASH_READ bytes and the window only guarantees coverage up to that end — a gate hit followed by a sub-8-byte block read past the window. On the bulk/MT paths the window borrows the caller's slice, so that is a real heap overread (ASAN: `READ of size 8` right past the input region); streaming read stale capacity bytes (UB under the strict model). Every other fill path already stopped at `len - HASH_READ`; the bound is now `(block_start - win_base).saturating_sub(HASH_READ)` — also exactly where a scan of the gated block would have stopped inserting, so table state stays scan-equivalent. Output was always valid (garbage entries only steer probes into byte-verified misses), and the trigger needs gate→tiny-block sequencing, which is why ordinary roundtrips never saw it.
- Small-literal u64 copy: the read side must be guarded with `anchor_idx + 8 <= win.len()` (write-side overflow is harmless; read-side OOB intrudes into illegal memory).
- Loop guards use `saturating_sub`: miss stepping can cross block_end, and unsigned subtraction wraps into a huge value.
- insert_max subtraction: when the first block is <5 bytes, `win_base + win.len() - MIN_HASH` underflows → compute lazily or use saturating_sub.
- **An inclusive bound clamped with `.min` does not make an empty range safe**: `insert_max` is the *last* insertable position (inclusive), but `insert_covered` used it as an exclusive loop end and then computed `(end - p) & 1` for the odd-position peel. A match *starting* past the bound leaves the range empty, the u64 subtraction wraps, and an odd wrapped difference fires the peel — hashing 8 bytes at a position past the window. Two live trigger paths, not just tiny inputs: first blocks < 9 B (insert_max saturates to win_base) **and** `rep1_chain` tails on ordinary inputs (its scan bar is MIN_MATCH of block_end, so `start` can sit up to 4 past the bound; the streaming ring buffer swallows those 1-4 byte overreads — only bulk inputs whose window ends at the allocation end are ASAN-visible, which is why the fuzzer needed an 8-byte reproducer). Release stays silent and output stays *valid* (the garbage table entry only steers later probes). Fix-shape A/B: guard branch and `.max(p)` cmov both +0.23% Ir json.fastest (+0.28% text), a subtraction-free peel-after restructure +0.54% (the `p + 1 < end` compare does not strength-reduce) — ship the guard, wall is flat on the branch/latency-bound tier.
- **A head-table insert without its chain link breaks the walk's induction (2026-09-16)**: the chain walk reads a candidate's chain slot after resolving it through the head table, so a head insert that skips the link (`insert_covered` via `TableEmit::emit` — the rep1 continuation's covered fill) parks a position whose slot still holds whatever a *previous* job wrote. The prefill doc's "stale link slots are unreachable" induction holds only if every head insert also links — the link-less form let a pooled stream-mt worker's job B walk terminate at a slot left by its own job A, making the frame bytes depend on the worker-claim order (±25 B on a 1.1 MiB job; run-to-run nondeterministic, invisible to fresh-process dumps). Bulk mt was affected in principle too and only looked stable through fixed claim order. Fix: `insert_linked_at` — the chain strategies link every covered head insert (`TableEmit::emit_linked`), the fast strategy's fills stay link-less (no chain). The linked fills also *improve* the chain band (levels 5-12 shrink 0.03-0.19% on json/text — covered positions become walkable candidates). Regression test: `pooled_state_reuse_is_output_neutral`. Lesson: any "stale X is unreachable" proof must be re-validated per insert path, not only per table (the induction was proven for the prefill grid and assumed for the emit path).
- **Distance-resolve of u32 table entries must exclude dist 0**: a stale slot can hold `pack_pos(pos)` of the *current* scan position — pooled tables reuse residue across frames (`327bc99`'s don't-clear design), and an old-cycle slot can alias anything. `dist = pos - entry + 1` then degenerates to 0, `dist <= reach` admits it, and the candidate byte-compares **against itself** — read4/extend trivially "match", the walk returns a zero-offset candidate, and the store gate's `(idx - cand).ilog2()` panics. The old `unpack_pos` wrap check (`cand >= pos → step one 4-GiB cycle back`) rejected this implicitly; the unsigned form `dist.wrapping_sub(1) < reach` (admits exactly [1, reach]) restores it at zero extra cost — the subtraction must be *wrapping* too: plain `dist - 1` panics in debug builds at exactly the dist-0 case it exists to reject (release wraps, so every dump/ratio gate passed while `cargo test` failed). Surfaced only in the interleaved matrix's timing loop (pooled state across rounds), never in fresh-process dumps — pool residue is a real input dimension the dump gate cannot see.
- **Every exit of a search must leave the same table contract (2026-09-19)**: `dubt::find_best`'s rep early-exit returned without inserting the searched position and with `next_update` still at it, so the *next* `fill_to` performed the position's insertion (nothing broke — the `pos >= next_update` guard inserts-before-search — but the exit contract diverged from the normal path's, and a long rep match's insertion was deferred into the following fill). Fix: the early exit writes the fill-form entry (head + chain link + unsorted mark — the head-link requirement is the induction pitfall above) and `next_update = max(next_update, pos+1)`, which is state-equivalent to what the deferred fill produced, just earlier. Lesson: a multi-exit search owns one postcondition — "searched position inserted, `next_update` past it" — and each new early exit must restate it, not rely on the next fill to clean up.

## SPSC checksum ring

- **"Single producer" means single thread, not single frame**: nested/overlapping frames (reentrant compress, two-frame same-thread tests) interleave into the same ring; any scheme that "caches the next_seq starting point at frame creation" lets two live frames claim the same seq and overwrite each other (the inner RESET gets clobbered → worker panics OOB → the main thread spins forever in FinishCell, pegging all cores). Correct: **each post reads the seq fresh from the shared head and claims it** (within a single thread, post is non-reentrant — reading is claiming); the producer keeps only the drain threshold locally.
- **Worker panic = hidden deadlock**: after a worker panics, every main-thread wait becomes a permanent spin pegging all cores; when investigating, first look for worker panic output under `--test-threads=1 --nocapture`, then pkill.
- Memory ordering: slot payload Relaxed → kind Release → head Release; consumer side head Acquire → kind Acquire → payload Relaxed, a chained happens-before; ring wraparound is guarded by wait_free_slot (independent of frame identity, naturally supports interleaving).

## Misc

- **A sentinel passed through a contracted helper is a debug-build time bomb**: btlazy's depth-0 rep probe priced the incumbent `best` even when the tree search returned nothing — `lazy_value`'s `debug_assert!(len >= MIN_MATCH)` fired on the `{off: 0, len: 0}` sentinel and `full_ladder_roundtrip` failed in every debug run (release passed: `s*0/4 - lazy_price(0) == 0`, *accidentally* the correct no-candidate baseline of 0). Make the sentinel's semantics explicit at the call site (`incumbent = 0` when `best.len == 0`) instead of relying on len-0 arithmetic to degenerate to the right value — the release behavior was never wrong, but nothing tied the two together.
- **btlazy2 selection: a repcode winner must keep its own off-base.** Collapsing the longest-rep candidate to `off_base 1` ("it's a rep") emits the wrong offset whenever the winner is the rep1/rep2 form — roundtrip fails only on rep-dense data and far into the stream (found at ~4 MiB on json). Same class as the ll0-form rule: off-base 1/2/3 each name a *different* decoder action at ll==0 (swap, rep2, rep3) and a *different* plain repcode at ll>0.

- Streaming 128KB trailing-empty-block quirk: when Stream fills the tail it cannot know EOF in advance, must do a second read that triggers 0, and emits one extra 3-byte raw last block; the slice path must explicitly mirror trailing_empty for bit-identical output.
- **opt.rs (zstd_opt port) details**: debug eprintln under `#[cfg(feature="std")]` gets compiled into release builds with the default feature (once silently flooded stderr); `ZSTD_count` returns a pointer difference — when continuing a count you must **replace**, not accumulate; rep history is updated once per series by the path walk (emitter-side per-seq updates are the decoder-equivalent semantics — pick one; duplicate updates always blow up); the insert-into-tree counting cap belongs in the DP window (4096 slots) — otherwise regions skipped by the parser get re-counted from stale heads (the lesson behind text 45→313 MiB/s).
- Corpus-generation narrow integers: `(i as u8 + 1)` panics on debug addition overflow at i=255 (u8 truncates first, then +1); compute in usize and cast afterwards.
- Gain-gate semantic drift: C's +7 is the margin for "whether a later candidate **replaces** the already-held match", not a store gate; putting the gate on the store decision (stricter than C) is deliberate (our tables are denser), but know the cost: short-distance matches in text get falsely killed.
- **Hidden constraint on the FSE transition-table packed width**: the u32 entry's baseline keeps only 9 bits (tables ≤512 states); production acc_log ≤9 (huff0 weight table 6, sequence table 9) never overflows; fuzz_exports `round_trip` with max_log=22 builds a log10 table → baseline≥512 silently truncated → the encoder writes diffs exceeding the packed width (debug asserts blow up under fuzz; release silently emits a misaligned stream). Fix: widen the layout to 12+4+12 (`optimal_table_log` already clamps to 5..=12), `build_table_from_counts` clamping to 12 plus a `build_table_from_probabilities` debug_assert as double insurance. **Lesson: implicit limits in bitfield packing must be enforced at the construction entry; parameter ranges "production never uses" will sooner or later be stepped on by fuzz or later extensions.**
- **ST encoding output depends on in-process history (matcher state-pool residue)**: the thread_local matcher state pool persists across frames (the `327bc99` don't-clear-u32-tables design); the same input can produce **different but each valid** frames under different in-process histories (Level::Fast, 24B input measured: streaming 37B raw block vs bulk 35B). Symptom: within a single process, "passes sometimes, fails sometimes". Constraints: cross-build byte comparisons must use a fresh process (that is the dump tool's purpose); the cross-check oracle uses two-sided decode validity rather than byte equality (that is what encode_stream fuzz does). The same problem for MT jobs was fixed by table clearing in a6cf8a6 (the ST variant of pitfall 20). If libzstd-style "same input, same output" determinism is ever wanted: reset with table clearing (speed cost) or the frame-epoch scheme (see the pitfall-20 argument in WORK.md).
- **Trainer: sorted sample concatenation poisons LMC selection** — the fastCover epochs partition the concatenated training body; with a sorted (alphabetical, glob-ordered) body every epoch is a cluster of near-identical files, each epoch's best segment describes its *cluster* instead of the collection, and the positional 75/25 train/test split lands on a distribution shift. On the systemd fixture this alone was worth ~20% dict quality (holdout 7,371→6,030 B at matched k, referee libzstd -9). Fix: fixed-seed Fisher-Yates over sample order before concatenation (libzstd's `DiB_shuffle` port) — deterministic AND representative. Related measurement trap: `zstd --train-fastcover=k=K,d=D` (forced parameters, non-optimizer path) trains on **all** samples — the 75/25 split exists only in the optimizer — so forced-k dicts leak the test set in A/B comparisons (a leaked k=537 dict scored 5,685 vs the honest 6,085).
- **Trainer unit-test noise must be aperiodic**: `(i*131 + j*17) as u8` noise repeats its 8-grams ~30× across files (all files land on the same 256 k-mers mod 256 arithmetic), and a 61-byte pattern repeated 8× lets a shared/noise-straddling window cover *all* distinct shared k-mers plus free noise coverage — both made the "noise" out-score the shared block. LCG noise with per-file seeds and a non-repetitive shared block keep the assertion meaningful.
- **Dictionary entropy preloading through between-block heuristics is net-negative** — the seeded tables must compete on measured costs, and the tuned heuristics starve them three separate ways (2026-09-16, cross-fed-dict decomposition on the systemd holdout): (1) the huffman treeless gate `diff > 5` (sum of code-length differences) rejects dict tables that would win by tens of bytes — the right comparison is stream bits vs stream bits + the exact serialized description (`HUF_estimateCompressedSize` form); (2) the FSE predefined thresholds (nb_seq < 72 → predefined) fire BEFORE the repeat check, so dict tables never reach the small blocks where their statistics matter — libzstd's lazy+ path compares predefined/repeat/fresh purely on costs; (3) treeless blocks below 1 KiB should take the single-stream literals form (no 6-byte jump table, one padding tail instead of four — libzstd emits it whenever `repeat_valid && lhSize == 3`). Landing all three took zstdx -9 + our formatted dict from +11.6% to +3.0% vs libzstd on the holdout, and flipped the formatted-vs-raw delta from +3.1% (worse than raw) to -5.7%. All of it is gated on a per-stream "still dictionary statistics" flag — every no-dict path keeps the stock selection (full-ladder dump byte-identical).
- **Cross-fed dictionaries decompose an end-to-end dict gap in one pass**: train both trainers on the same corpus, then run {our encoder, libzstd} x {our raw content, libzstd raw content, libzstd formatted} over the holdout. Same-encoder raw-content pairs isolate trainer quality; same-dict encoder pairs isolate the encoder; formatted-vs-raw per encoder isolates the entropy-preload handling. On this fixture that split showed trainer parity, an encoder-side +7.8% small-band residue, and an entropy component that was actively harmful for us — three different levers, one measurement.
- **Dictionary content is not an MT strip — fill density follows the load semantics (2026-09-18)**: `load_dictionary` had routed through `prefill_window`, inheriting the strip's stride-3 grid (and Fast's retention-tail cap) that exists because a window-long strip cannot afford a dense fill. A dictionary is at most one window and the payload parses mostly against it, so coverage — not fill cost — dominates: libzstd fills chain rows densely (`ZSTD_insertAndFindFirstIndex`), and the CLI's small files go through CDict-attach whose tables carry the `dtlm_full` backfill. Reusing a strip-tuned prefill for another consumer of the same tables silently dropped 2/3 of the dict's candidates (chain) or the whole dict head (fast's cap); the level fingerprint was a chain-row-only end-to-end gap (-9 worst, -3/dfast at parity — both sides stride-3 there). Corollary: the dict chain path needs no `acquire_seed` once dense (measured byte-identical — the seed's period-repeat compensation is for single-candidate head tables, and dense links already reach every position). Second knob in the same class: our `search_depth` table halves libzstd's `1 << searchLog` attempt counts as a big-payload speed tuning — parity-preserving there, but a dict parse walks a long dense chain where the full budget converts (+2.1 → +1.9% raw control at -9 on top of the fill fix).
- **Filter seeding is phase-critical, not density-critical (2026-09-17)**: seeding the incompressibility gate's repeat probe from a job strip with one whole-strip stride hits a modular lottery — a period-P repeat probes a hit only for blocks whose sample grid happens to align with the seed stride mod P/gcd, so on a synthetic 5 MiB-period corpus four of five jobs lost the far class while the one job whose strip length picked a coprime stride kept it (12 MiB strip → derived stride 385 = 5·7·11 shares factors with the block stride 33; 8 MiB → 257 prime, lucky). The fix replays the consumer itself: same block-sized segments, same per-segment stride, same phase restart — a repeat at a block-multiple displacement then lands on the segment grid a scan would have planted, always. Any future "pre-plant a sampled filter from history" must copy the consumer's exact sampling geometry; matching its density is not enough.

- **An incompressibility pre-gate must price the candidate it guards (2026-09-18)**: the literals gates' flat ~160 B description term assumed the block would build a fresh huffman table; on dict-seeded streams the leading candidate is treeless (zero description bytes), so the gate rejected every small-literals block a dictionary table would have compressed to 2/3 size while libzstd's repeat path — no pre-gate, exact post-encode size compare — took the win. Fingerprint: formatted-dict cells trail their raw-content control while the sequence sections measure ahead; the entropy machinery looks guilty while the leak is a guard's cost model. Corollary: a guard that exists only to skip wasted encode work (an exact post-encode comparison already decides the outcome) may only bias toward attempting more — never toward rejecting what the exact comparison would accept.

- **Stream drain must track partial writes, never clear on error (2026-09-19)**: `write_output_to` used `write_all` + unconditional `output.clear()`, so a writer that half-accepts a buffer and then errors (WouldBlock/WriteZero on a socket/pipe) silently dropped every undelivered encoded byte — the caller's retry continued from a shifted position and the frame shipped with a missing stretch, surfaced only as a decode failure far away. Fix: an incremental `write` loop advancing the `out_read` cursor (`split_output` already had the right shape), clearing only after the drain completes; both cores share `encoder_core::write_pending_output`, and the Ok(0) verdict mirrors each build's `write_all` (std: WriteZero, no_std: WriteAllEof). Corollary: `write::Encoder::write` still stages its input BEFORE the drain, so on Err the input may already be accepted — a caller retrying per the io::Write "Err = nothing written" contract would duplicate data. Closing that gap needs input deferral (a copy per write on the hot path); until some caller needs retry-same-buffer semantics, the divergence is documented at the impl instead.
- **The read-side encoder's `finish` dropped the undelivered output it was about to close over (2026-09-19)**: `read::Encoder::finish` ran `core.finish()` (emitting the last block + checksum into `core.output`) and then returned the inner reader, dropping `output` with it — the caller had already read only a prefix without the closing block, i.e. a truncated frame, and unlike the write side there is no later drain that could deliver the tail. Contract fix: `finish` fails with `Error::UnreadOutput { bytes }` unless the encoder was read to end of stream first (the final read's `Ok(0)` both finishes the core via the pump and drains the output); the shape "a delivery endpoint vanished while bytes were still pending" is the read-side twin of the drain pitfall above. Lesson for the API: a `finish` that hands back the wrapped resource can only succeed when nothing is in flight — make the pending state an explicit, countable error instead of documenting the loss.

- **One write_all sized the reserve to the whole slice (2026-09-19)**: the mt stream write path handed `make_space` the entire remaining input as its growth target once the buffer filled, so a single `write_all` of a multi-hundred-MiB slice reserved exactly that much — `BUF_CAP_MAX`'s "past the cap the wrap alone recycles" bound never engaged on this path (the read-side `pump_direct` is bounded per pull and was unaffected). Fix: the full-buffer write step asks for one bounded increment (`PUMP_STEP_MAX`, the same bound as a direct read pull); the loop refills and re-recycles, and each step's posts keep completed jobs widening the wrappable dead prefix, so the capped steps progress instead of spinning (a bounded want ≥ 1 at a full buffer always wraps or grows). The proactive doubling ladder below the cap is untouched, so steady-state buffer sizes — and the frame bytes (the job grid is a pure function of stream offsets) — do not change.

- **A pledged size is a hard contract, not a hint (2026-09-19)**: both stream cores wrote `options.pledged_size` straight into the frame header and never compared it with what was actually fed — a stream pledged 10 bytes but fed 20 (or pledged 100, fed 20) produced a normal-looking frame declaring FCS=n over content ≠ n, which every decoder rejects (libzstd checks the pledge mid-compress and at the frame tail; the CLI pledges the stat size and then `io::copy`es, so a file changing under it silently shipped a broken frame). Fix: libzstd's split — the first write whose bytes push the fed total past the pledge fails that write itself (`srcSize_wrong` at the first overrun, nothing staged, deterministic), and both core `finish`es catch any residual mismatch before emitting the closing block. What finish can NOT promise is "no frame byte emitted": `write::Encoder::write` drains eagerly, so the sink may already hold the header and completed blocks — the surfaced failure is a truncated, unclosed frame, which is the honest outcome (the first version of this fix claimed byte-level prevention; do not re-claim it). Lesson: anything written into a frame header as fact must be verified against reality at the earliest boundary that can observe the lie — the write that crosses it, not just the finish that closes it.

- **A windowed frame cannot declare the 1-byte FCS class (2026-09-19)**: flag 0 means the Frame_Content_Size field is ABSENT unless the single-segment flag is set, but the header serializer mapped every width-1 size (0..=255) to flag 0 and appended the 1-byte field anyway. Any pledged stream or bulk-mt input below 256 bytes (the CLI pledges every non-empty file's stat size) serialized a stray byte that shifts the first block header: both this crate's decoder and libzstd reject the frame ("incomplete frame"/"Data corruption"). All boundary classes at 256+ worked, so every ordinary roundtrip test passed. Fix: `FrameHeader::serialize` normalizes — a windowed frame below 256 bytes drops the declaration (the pledge keeps shaping the encode; only the header promise is lost). Lesson: descriptor-flag tables need a test per flag class crossed with the flags that redefine them (single_segment redefines flag 0), not just per field width.
- **A poison's flag must never precede its payload (2026-09-19)**: the stream-mt worker's panic path aborted its job (slot filled empty), then flipped the `poisoned` mirror flag, then stored the payload under the queue lock — a two-step publish. The posting thread could observe flag-set/payload-absent in between: `surface_poison` surfaced nothing, `drain_all` assembled the aborted job's empty slot like any completion and returned a frame missing the poisoned job's bytes as Ok, the payload stranded in the worker (the bulk path is immune — payload under its mutex first, then the slot). Fix: `QueueShared::publish_poison` orders payload → flag → abort; the abort must also stay after the flag, or the assemblable-empty job drains ahead of the payload it implies. The drain's "pending empty → surface → return" arm is safe only because a set flag now guarantees `inner.poison` holds the payload; `surface_poison`'s flag-set/payload-absent early return is unreachable and stays as fail-safe only. Lesson: a fast-path mirror flag of mutex-guarded state is a second publication — it needs its own happens-before story, not just the mutex's.
- **A knob only some consumers honor must be refused at the arming point, not ignored (2026-09-19)**: `prepare_job_state` armed the deep-offset ramp (`ZSTDX_MT_RAMP_BYTES`) on every MT job, but only the fast/dfast/chain parses read the gate — the btlazy2 (13-15) and opt (16+) rows silently produced unconstrained frames under the env, so a piece-decode experiment on those levels measured nothing: the frames are legal, but their crossing reads are of unbounded shallowness, which fails the piece executor's validation (or, on shapes whose reads happen to run deep, slips past it and fakes engagement). `MatchGeneratorDriver::arm_ramp` now panics on `BtLazy`/`Opt`; the tree rows' wiring points are enumerated in its doc comment (`dubt::find_best`'s rep loop and sorted descent, `btlazy::run_block_lazy`'s two `rep_probe`s, the literal-offset backward extension floor, the LDM far-candidate check, plus the opt DP walk). The panic must be unconditional (not a `debug_assert`): release is where the experiment runs.



- **The donated probe span must arm as the kept frame's job zero (2026-09-19)**: the reach probe's donation hard-armed [`LdmArming::Job`], but a Keep verdict can re-grid the frame onto the mid-size prefix-LDM capture (bulk `plan_prefix_ldm`, stream `engage_midsize_capture`), whose jobs arm `JobPrefix` — the capture's source-clamped window (the W25 band) sits below the `Job` bar, so the donated state's LDM never armed while jobs 1+ armed. Job zero lost the far candidates inside its own span and the frame diverged from the undonated schedule (32 MiB tiled row-9 frame at w2: 7.94 MB vs 4.76 MB, +67%; invisible at w≥4 because a job at the W22 strip floor has no beyond-reach distances). The arming is decidable before the verdict — the capture engages exactly when a Keep verdict would run it — so the donation gate computes the capture plan first and arms the donation with its arming (the Shrink verdict pays the span's split pass for nothing, the band's price); debug asserts pair the frame's capture with the donation's arming on both paths. Lesson: a "the donated span IS job zero's parse" contract must arm the donation from the job's final schedule, never from the pre-verdict default.

- **A pledged stream's initial reserve is a scheduling scale, not a need (2026-09-19)**: the mt stream's initial and probe-settle reserves sized to `workers × initial_job + overlap` — with the CLI always pledging the file size, a 16 GiB file at -T8 (job size at the `MAX_JOB_SIZE` 1 GiB ceiling) reserved ~8 GiB up front and held the first that-much input resident for the whole stream, because the pump only recycles at a full buffer. Fix: cap both reserves at `BUF_CAP_MAX` (the same ceiling the unpledged growth ladder already runs at); the pump grows into the live need through `make_space`, whose wrap recycles at grid lines where quiescence is reachable, and `make_space`'s growth arm still exceeds the cap when the live set demands it (a pledged grid's held-back final job). Note the floor that remains: the fixed grid's first job cannot post until a full job-size is buffered, so the buffer still grows to ~1 job + strip mid-stream — that is the grid's own semantics, not the reserve.
